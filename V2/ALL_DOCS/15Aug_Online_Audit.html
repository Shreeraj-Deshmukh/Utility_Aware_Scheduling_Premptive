DATE · 2026-08-15 SCOPE · usrt/online/* α=0.15 · β=1.0 · B=400 INSTANCE · testcase.py (6 tasks, 30 jobs, 2 cores)

Verdict in one paragraph. The online DP machinery is correct — the worked-example tables reproduce the design document exactly, the energy pool is race-safe, and the commit path never violates timing or the budget. The frequency machinery is also present and functional: the action set enumerates every frequency, and at a tight budget the DP demonstrably fires the paper’s Option 3/4 conversions (including a textbook pure Option 4). The problem you are sensing is real but it is not a bug — it is that frequency is inert in the exact configuration you are testing (B=400). The offline schedule pins every job at fmax, and at B=400 energy is nowhere near binding, so online frequency change has (a) no headroom upward — you are already at fmax — and (b) no incentive downward — energy is abundant. The lever only wakes up when the budget forces the offline baseline below fmax. This audit shows the evidence and the fix.

1 · Scope & method

This reviews the online phase only — the files under usrt/online/ (actions.py, value_function.py, dp.py, controller.py, energy_pool.py, density.py, simulator.py) — driven by usrt/solvers/online_demo.py on the current testcase.py. The reference is the uploaded paper “Utility aware Energy Constrained Real-Time Scheduling”, §VI (Online), plus the design-doc addenda.

Method: (1) read every online module against §VI; (2) trace the value flow end-to-end; (3) instrument the actual run and, crucially, vary the energy budget to isolate whether frequency behaviour is a bug or a regime effect. All numbers below are measured, not asserted.

The design under review (locked earlier): one precomputed breakpoint DP per processor (time slack is processor-local), and a single global energy pool shared by all processors, guarded by a binary semaphore. Cross-processor energy contention is resolved by future-utility-density arbitration. This maps cleanly onto §VI (“time slack — per processor; energy slack — global”) and the §VI improvement bullet “Two DP with shared Energy”. That structural choice is sound and is not what this audit disputes.

2 · The paper’s online model (§VI)

On the early completion of a job, its freed time slack Δt (processor-local, non-accumulative) and energy slack Δe (global, accumulative) are distributed over downstream jobs by choosing, per job, one of four options:

OptActionΔtΔeUtilitySign in code (a_t, a_e)
1Release next job, save Δt, Δekeepkeep0(0, 0)
2Execute additional optional segment(s)spendspend+(+, +)
3Decrease frequency → banks energy for laterspend+gain0(+, −)
4Increase frequency → banks time for later+gainspend0(−, +)

The distribution is a right-to-left DP over V[j][Δt][Δe], reusing the downstream solution — exactly the recurrence implemented. Note two facts the paper fixes and the code inherits:

  • Frequency is per-job and mutable across jobs (Task Model: “jobs of a task may execute with a different frequency; once a job starts it cannot change frequency”). So online re-selecting the frequency of a not-yet-started downstream job is legitimate — Options 3/4 depend on it.
  • Utility depends only on segments (Eq. 8: utility ∝ Σei,q, the fmax-normalized work). Frequency changes carry zero utility of their own — they are pure time↔energy converters.

3 · Architecture as implemented

The value flow on one early completion, module by module:

early completion (i,j) with windfall (Δt, Δe)
        │
controller.on_completion
        │  1. eff_override[(i,j)] = actual eff;  pool.refund(Δe)         [energy_pool]
        │  2. densities = future_utility_density(all procs)             [density]
        │     caps      = arbitrate_energy(pool, densities)  → de_budget
        │  3. dp_value, planned = dps[x].distribute(c+1, Δt, de_budget) [dp → value_function.query]
        │  4. committed = _commit_with_guarantee(x, planned)
        │        · dynamic per-processor DBF (credits completed jobs)
        │        · pool.try_spend / try_spend_batch  (atomic, semaphore) [energy_pool]
        │        · GRACEFUL DEGRADATION: retry k-1, k-2, … each DBF-checked
        │  5. rebuild dps[x]  (baseline changed → keep later lookups exact)
        ▼
returns (added_utility, [JobDecision…])

The per-job action set (actions.py) — where frequency enters

for k in range(k_off, N_seg_i + 1):          # may only ADD segments (A1)
    gain = u_i * (cum[i][k] - cum[i][k_off]) # utility: f-independent
    for z in range(len(freq_set)):           # EVERY frequency considered
        a_t = e_eff(cum[i][k], f_z) - base_eff
        if a_t > time_cap + tol: continue    # window-slack gate
        a_e = energy(cum[i][k], f_z) - base_en
        actions.append(Action(a_t, a_e, gain, k, z))

So the action set is the full 4-option model: z < z_off gives Option-3-flavoured actions (a_t>0, a_e<0); z > z_off gives Option-4 (a_t<0, a_e>0); and combined (k>k_off, z≠z_off) actions are all present. The value function (value_function.py) keeps only the Pareto-non-dominated (req_t, req_e, value) points, so frequency options survive only when they are genuinely efficient. This is faithful to §VI. The catch is entirely in the baseline those actions are measured against — see Finding A.

4 · The energy/frequency regime — why this matters

Everything about frequency behaviour follows from the energy-per-unit-work curve g(f) = α/f + β·f², minimized at f* = (α/2β)1/3. With the current α=0.15, β=1.0, f* = 0.4217. Measured over the instance’s frequency set:

The single most important fact for this regime: running at fmax costs 2.15× the energy per unit of work compared with f≈0.4, but it also runs 2.5× faster. So frequency is a live time↔energy dial — and which way you want to turn it depends entirely on which resource is scarce. That is exactly the question §VI’s Options 3/4 exist to answer, and exactly the question the current test budget never poses.

FINDING AHigh impact

Online frequency options are inert at B=400 — and it is the offline fmax pin, not the DP

What you observe. Run python run.py testcase.py online (B=400) and not one committed decision changes frequency; every online gain is a plain segment addition. That is what makes it feel like “frequency is not being considered”.

Why. Two compounding causes, both outside the DP:

  1. Offline pins fmax. Both online_demo.py:49 and the v5b solver initialise freq_idx = N_frq − 1 for every job, and Phase 4 only scales down when the schedule is over budget. At B=400 it is under budget, so all 30 jobs stay at fmax (measured histogram: {1.0: 30}). Since zoff is already the ceiling, Option 4 (increase frequency) generates zero actions — there is no z > z_off.
  2. Energy is not binding. Offline energy 274.16/400 leaves 125.8 slack; even after the online phase, WCET-committed energy is 304.6/400 and realised only 213/400. With energy this abundant, Option 3 (slow down to save energy) has no downstream customer — the DP correctly never chooses a zero-utility conversion nobody needs. The binding constraint here is time (DBF window slack), which fmax already minimises.

Proof it is a regime effect, not a bug. The same code, only the budget changed, exercises the full option set the moment energy binds:

If the paper’s DVFS contribution is to be demonstrable, this configuration cannot be the one you report from — see Recommendations 1 & 2.
FINDING BMedium

Offline scaling targets feasibility, never the energy-optimal frequency

Even when the budget forces scaling (B=200/165), Phase 4 stops the instant the schedule fits (aggressive.py: “reduce only as far as needed”). The resulting frequencies cluster at 0.6–0.9 and never approach f*≈0.4, the genuine energy-optimum. Phase 5’s frequency moves (Case ii.A “raise f of j*”, ii.B “lower f of others”) are local trades to land one more segment, not a global choice of operating point.

Magnitude of what is left on the table. The mandatory work alone sums to ≈159.8 fmax-units. Executed at fmax that is 159.8·1.15 ≈ 183.8 energy; at f=0.4 it would be 159.8·0.535 ≈ 85.5 energy — a ≈98-unit saving that could buy many more optional segments. (You cannot move everything to 0.4 — effective utilisation 1.33 × 2.5 = 3.33 > 2 breaks timing — but a well-chosen subset can.) The heuristic never searches this trade globally, so in the energy-binding regime it is genuinely sub-optimal on utility, not just on frequency cosmetics.

This is an offline deviation, but it is the direct upstream cause of Finding A: the online phase can only convert around whatever baseline offline hands it.

FINDING CModeling consequence

Utility is frequency-independent ⇒ frequency is a pure converter, never a goal

gain = u_i·(cum[i][k] − cum[i][k_off]) — no f term, matching paper Eq. 8. This is correct, but it has a consequence worth stating plainly so nobody expects otherwise: the DP will change frequency only as an instrument to enable a downstream segment (Option 2) somewhere, or to satisfy a timing constraint. When neither is needed, “stay at the offline frequency” strictly dominates any pure conversion (equal utility, non-negative requirements). This is why a frequency lever with no scarce resource to relieve looks dead — it is meant to be dead in that case. It becomes valuable exactly when one resource is scarce and the other is slack, which is the tight-budget regime.

FINDING DMedium

Scalar-Δt DP over-plans; the commit-time DBF trims the excess

The DP distributes a single scalar Δt across a whole downstream chain, and the per-job time cap is the full deadline interval (controller.py:113) rather than the tight window slack — so the DP is an optimistic upper bound that the dynamic DBF then trims at commit. Measured at B=400: DP promised 72.90, committed 68.36 → 4.55 utility lost to trim over a single event (T4,j1). Graceful degradation (retry k−1, k−2…) already recovers most of it; the residual 4.55 is the price of the scalar (vs per-window vector) time state. Orthogonal to frequency, but part of an honest online audit. Fix direction: per-window / per-nesting-level Δt state (Recommendation 4).

FINDING ELow–Medium

Aggregate-states quantization clips the exact Pareto frontier

With DVFS active the exact frontier explodes; value_function._aggregate caps each level to ~256 points on a 16×16 grid (cell ≈ span/16). Measured: the uncapped frontier reaches ≈16 400 points/level (a cap-20000 build took ~30 h), clipped to ~229 at cap-256 — a ~70× reduction at a resolution of ≈3.8 time × 2.0 energy per bucket at the largest level. This is feasibility-safe (dropping options can only lower a reported value, never overstate an unachievable one), so it is bounded sub-optimality, not a constraint risk. But it is the largest source of DP inexactness once frequency is genuinely in play, and it interacts with Finding A: a coarse grid can bucket away precisely the low-req_e conversion points Option 3 relies on. Worth a sensitivity sweep if DVFS is promoted to a headline result.

FINDING FLow

Proportional density arbitration can under-serve immediate high-value work

density.arbitrate_energy caps each processor’s pool claim by its future utility density. With two processors and abundant energy this rarely bites, but under scarcity it can reserve energy for a processor whose valuable work is far in the future while a processor with an immediate high-value segment is throttled. This is the paper’s own “approximate — consider the job with higher future density” answer, so it is by design; flagged only as a known sub-optimality and a candidate for the §VIII.B marginal-opportunity-cost routing (Recommendation 5). The hard guarantee (total energy ≤ B) is never at risk — the atomic try_spend enforces it regardless of arbitration.

FINDING GInfo

Smaller code observations

  • Stale docstring. models.py still says “With ALPHA=1.0, BETA=0.5 the minimum energy is achieved at f_max” — true for the old constants, misleading now that α=0.15, β=1.0 put the optimum at f≈0.42. Update it so the next reader isn’t misdirected on the very point this audit is about.
  • Batch spend nets mixed signs. try_spend_batch spends sum(amounts) atomically; a batch mixing Option-2 (+a_e) and Option-3 (−a_e) is judged on its net. Order-independent for a single scalar budget, so correct — noted only so it isn’t mistaken for a per-decision check.
  • DP rebuild every event. on_completion fully rebuilds the affected processor’s DP after each completion (step 5). Correct and keeps later lookups exact, but it is the dominant cost of the ~77 s sim; the §VI “Lazy DP” improvement targets exactly this.
  • time_cap = full deadline interval. Intentional (documented) to let the DP over-plan and rely on the commit DBF — but it is the mechanism behind Finding D, so keep the two linked in your mind when tuning either.

6 · What is provably correct (so nothing is over-alarmed)

  • DP core matches the design document exactly. worked_examples.verify() reproduces every cell of the published V[j][Δt][Δe] tables and all three verified traces (19.0, 17.0, 10.0). The compose/prune/query breakpoint machinery is pinned.
  • Frequency is fully represented in the action set — all four options, including combined segment+frequency moves — and is demonstrably exercised when energy binds (Finding A table).
  • Energy safety is airtight. The single global pool’s atomic check-and-deduct (try_spend) makes C3 (total energy ≤ B) un-violable even under concurrent processors; measured run: denied=0, pool never negative.
  • Timing safety is honest. The dynamic per-processor DBF credits already-completed jobs’ actual execution, so added downstream work never pushes a window above its original feasible demand — no real deadline miss is ever admitted. Graceful degradation keeps the guarantee while recovering utility.
  • Decisions are deterministic and constraint-respecting — never the probabilistic accept/reject the offline baseline heuristic uses.

7 · Recommendations (prioritized)

  1. Stop pinning fmax offline; hand the online phase a two-sided baseline. This is the highest-leverage change and it directly answers “we’re not considering frequency”. If the offline schedule commits jobs near the energy-efficient feasible frequency instead of the ceiling, then online Option 4 regains upward headroom and Option 3 has a live customer — the full §VI option set becomes reachable in every budget regime, not only tight ones. Minimal version: after Phase 5/6, add a base-frequency selection pass that pushes low-utility-density jobs toward f* while DBF-feasible, banking energy for more segments.
  2. Report the online phase from an energy-binding budget. B=400 makes energy a non-constraint, which structurally hides DVFS. Run the headline online experiments at a B where offline energy ≈ budget (here B≈180–220): the mechanism activates, Options 3/4 fire, and the paper’s contribution is visible and defensible. Keep B=400 only as the “energy-slack / time-bound” regime contrast.
  3. Make offline frequency selection energy-aware globally (Finding B). A pass that chooses each job’s operating frequency by marginal utility-per-energy — not merely “scale down until feasible” — closes the ≈98-energy gap in the binding regime and typically buys real utility.
  4. Exact per-window / per-nesting-level Δt state (Finding D). Replaces the scalar Δt with a vector so the DP stops over-planning; recovers the residual trim loss (4.55 here) and lets you drop the runtime DBF from the critical path.
  5. §VIII.B marginal-opportunity-cost energy routing (Finding F). Ration the shared pool by marginal ΔPx(c) only under scarcity, rather than a static proportional density split.
  6. Aggregate-states sensitivity sweep + Lazy DP (Findings E, G) once DVFS is a headline: confirm cap-256 is not clipping load-bearing conversion points, and make the per-event rebuild incremental.
