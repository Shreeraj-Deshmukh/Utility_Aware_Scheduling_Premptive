0. The DP Approach in One Screen

At each early completion, a job that finished before its WCET frees a time windfall Δt (processor-local) and an energy windfall Δe (global). A precomputed dynamic program decides, optimally, how to spread that windfall over the downstream jobs to maximise added optional-segment utility.

V[j][Δt][Δe] = max(at, ae)  { gain(j, at, ae) + V[j+1][Δt − at][Δe − ae] }

Exact breakpoint representation. Each value-function level is stored not as a dense grid but as the Pareto frontier of (req_t, req_e, value) tuples — the finite set of reachable cumulative cost vectors. This is exact (no quantisation) and naturally "aggregated."

Per-processor + global energy. Time slack is local, so one DP is built per processor; the single global energy pool is arbitrated across processors by future utility density.

Full 4-option actions. Each downstream job may re-pick (k′ ≥ k_off, z′); signed (at, ae) deltas encode spend / save / time→energy / energy→time.

Validation: all 7 published tables (V[1]–V[4] across both worked examples) and all 3 traces (19.0 / 17.0 / 10.0) reproduce cell-for-cell — see usrt/online/worked_examples.py.

1. Assumptions

#AssumptionWhere / why
A1 Online only ADDS segments (k′ ≥ k_off). Offline-committed optional segments are never dropped online. actions.py — the action loop starts at k_off. Matches the paper's "execute additional optional segments." Removing committed utility is out of scope.
A2 Δt is a scalar planning budget per processor chain; the DP does not model the full preemptive-DBF window lattice during planning. Doc Issue 4. The exact constraint is re-imposed at commit time by the dynamic DBF (see A6), so the scalar is a planning proxy, never the feasibility authority.
A3 Global energy contention is resolved by proportional future- utility-density share (parameter-free default); strict priority optional. density.py. The doc's Approach C; it is explicitly a heuristic ordering, not a joint optimum (see L3).
A4 Costs come from the paper's energy model; gain depends only on k′. at, ae are signed deltas vs the offline baseline; utility is earned on fmax-normalised work (paper Eq. 8). actions.build_job_actions via models.energy_val / e_eff_val.
A5 Frequency may be re-selected online before a job starts. The paper forbids changing frequency once a job starts; the online decision is taken at the prior completion, before start — so this is consistent, not a violation.
A6 Feasibility binds on REALISED execution, not worst-case. The commit-time DBF credits each completed job's actual (reduced) effective time; energy binds on the realised pool (B − actual_consumed ≥ 0). controller._timing_ok_dynamic, controller.energy_pool. This is the correct notion for an online phase (see L1-note and Compromise C1).
A7 Time is genuinely per-processor; energy is the only cross-processor coupling. Doc Section 5. Justifies independent per-processor time DPs + centralised energy arbitration (avoids the Tm blow-up).
A8 Simulator ACET model: actual = ratio × committed effective time; energy freed proportionally (Δe = (1−ratio)·Ecommitted). simulator._windfall. A modelling choice for the demo; the DP/controller are agnostic to how (Δt, Δe) arise.
A9 EDF execution order, deterministic tie-break (deadline, release, task, job); periodic tasks over one hyper-period. dp._edf_order. Inherits the offline model.

2. Limitations

Material

L1. Frequency-conversion options are inert under α=1, β=0.5

NOT IN CODEBASE · 4 Sep 2026L1 no longer applies. It was true only for α=1, β=0.5. The real limitation now is the one in [[15Aug_Online_Audit]]: the offline schedule starts at f_max, so online has no upward headroom — not that the options are inert.

Energy per unit work α/f + βf² is minimised at f* = (α/2β)⅓ = 1.0 = fmax. So Option 3 (lower freq to save energy) never saves energy and Option 4 cannot exceed fmax. The 4-option action set is fully coded and correct, but under these constants Pareto pruning discards every conversion action — the DP collapses to Save + Spend.

Consequence / fix: the implementation is already general; choosing leakage-dominated constants (e.g. α=0.15, β=1.0 → f*≈0.42) activates Options 3/4 with zero code change. Until then, the DVFS axis is exercised only structurally, not numerically.
High

L2. Scalar-Δt planning vs exact preemptive DBF (achieved ≤ DP value)

The DP threads time as one scalar budget along the per-processor chain. When a completion frees time in window W and the DP funds additions to several downstream jobs that do not all share W, the scalar model can be optimistic. The commit-time dynamic DBF then trims the infeasible subset.

Net effect: the result is always feasible (constraint safety wins), but the achieved utility can be ≤ the raw DP table value in those cases. For single-windfall sequential chains — including both worked examples — there is no gap (achieved = DP value, verified).
High

L3. Energy arbitration is greedy, not jointly optimal

Proportional (or strict) density share resolves cross-processor energy contention cheaply but can mis-prioritise — e.g. one processor with a single very-high-density job vs another with several medium jobs whose combined value is larger (the doc's own caveat). The exact joint state V[j][ΔtP0]…[ΔtPm−1][Δe] is exponential in m and was deliberately not built.

Observed in the demo: strict arbitration yielded +20.3 vs proportional +55.3 on the same offline schedule — the split rule materially changes the outcome.
Medium

L4. "Precompute once" holds per event, not for the whole run

A single completion is a pure lookup. But once a windfall upgrades downstream baselines, the affected processor's DP is rebuilt so later completions stay exact (controller._build_dp after each commit). It is cheap (chain length × actions), but it is a rebuild, not one frozen table for the hyper-period.

Future work: incremental DP update (patch only the changed suffix) instead of full per-processor rebuild.
Medium

L5. Simultaneous completions are serialised

The "two early completions sharing Δe" question (doc Section 5 / Improvements) is handled by processing events in release order and arbitrating the pool at each — an approximation of true concurrency, not a simultaneous joint decision.

Medium

L6. No proven polynomial bound on the Pareto frontier

Frontier size is bounded in practice by pruning (segments × frequencies per job, then Pareto-dominated points removed) and the prune is O(n²). Worst-case growth along a long chain is not formally bounded, and the prune is not the asymptotically optimal 3-D Pareto algorithm.

Low

L7. Doc Issue-5 bounds & Lazy DP not implemented

Exact breakpoints make the table sparse, so I rely on that sparsity rather than explicitly clipping by schedule-derived ceilings (∆t ≤ min-window-slack, ∆e ≤ Eslackinit) or doing Lazy DP. For very large optional- work sets the frontier could be larger than strictly necessary.

Low

L8. Reconstruction follows the precomputed split, not realised downstream ACETs

A completion distributes its windfall using the precomputed optimal split; it does not re-optimise against the actual ACETs the downstream jobs will later realise (those are captured by their own subsequent completion events). Within a single event this is exact; across events it is event-greedy.

Low

L9. Time perishability is enforced structurally, not on an explicit timeline

"Use-it-now-or-lose-it" time slack is enforced by the dynamic DBF (a window's demand can never exceed its length) rather than by an explicit expiry clock. We do not model partial carry-forward of unused Δt across non-adjacent windows.

Low

L10. Online quality is capped by the offline schedule

The controller consumes a fixed offline schedule (v5b) as its baseline. It can only add on top of it; a poor offline mapping/segment choice limits the ceiling of online gains. The online phase does not re-map or re-balance.

3. Compromises (deliberate trade-offs)

#CompromiseChoseGave up
C1 Feasibility model Dynamic DBF (credits realised early completions) — produces real online gains and is the honest online notion. Worst-case robustness of the final schedule: a static WCET re-check of the end state will look over-full, by design.
C2 Multi-processor energy Per-processor time DP + heuristic density arbitration — each table is N×T×E. The exact joint optimum over a shared Δe (intractable: Tm).
C3 State after upgrades Lazy per-processor rebuild on baseline change. A truly incremental DP patch (more code, marginal payoff here).
C4 Input schedule Reuse the v5b offline pipeline — clean integration, one command. Joint offline+online co-optimisation; online is strictly a top-up.
C5 DP/DBF disagreement Trim to a feasible subset (constraint safety first). Matching the raw DP table value in the rare optimistic case (L2).

None of these are probabilistic: every decision is the DP optimum, committed only if it provably satisfies the dynamic DBF and the energy pool — per the explicit "never drop a constraint" requirement.

5. The "API" From the Document → Code Map

No external or third-party API/service is used by the online phase — it is pure Python standard library (collections.namedtuple, random) plus the repo's own modules. The design document defines no code API; its "API" is mathematical notation, mapped to functions as follows:

Document conceptImplementation
The table V[j][Δt][Δe] list[Entry] per level, built by compose() (value_function.py)
Right-to-left recurrence build_processor_dp() (dp.py)
gain(j, a_t, a_e) + the four options build_job_actions() → Action(a_t, a_e, gain, k, z) (actions.py)
Online lookup at completion query() / OnlineController.on_completion()
Action table A (reconstruction) Entry.nxt chain + ProcessorDP.distribute()
Utility-density arbitration ρ_x(t) future_utility_density() / arbitrate_energy()

Entry point for the whole flow: python run.py testcase.py online.
