2 · Headline

A phase-ordering defect was found and fixed during this dry run. The heuristics were declaring infeasible on 34 instances that the ILP solved — because Phase 3 tested the energy budget at f_max and returned terminally, before Phase 4 (whose whole purpose is to lower frequency) could run. Fixing the test to compare against the cheapest-possible assignment lifted the heuristics from 50/90 to 82–84/90, matching the ILP. Details in §6. All results below are post-fix.

7 · The phase pipeline, as it stands today

Every phase is a separate module; the heuristic versions are different assemblies of them. This section documents the current logic, including the Phase 3 fix described in §8 and the frequency-trade work that followed it — so it supersedes the phase description in summary-1-Aug.html.

Invariant entering Phase 2: every job sits at f_max with zero optional segments. Phases 4–8 exist to convert the energy and timing budget into utility. Utility comes only from optional segments — frequency never appears in the utility function (paper Eq. 8), so it is purely a time↔energy converter.

Phase 1 — Quantum SPS mapping

Assigns each job to a processor using mandatory work only, at f_max. Runs one quantum at a time (the gcd of all periods, so every job boundary lands on a quantum edge). Per quantum [q_start, q_end]:

  1. Collect newly-arrived jobs plus any leftover deferred from earlier quanta.
  2. Classify each as mandatory-now (d == q_end) or deferrable (d > q_end).
  3. Pre-filter: if total utilisation exceeds remaining capacity, defer the latest-deadline deferrable jobs until it fits.
  4. Run DPS + SPS for a balanced assignment.
  5. Verify per-processor utilisation ≤ 1.0; defer more if violated.
  6. Commit and update the running proc_util.

Afterwards: a full mandatory-only DBF check at f_max, then greedy repair if any window fails. Load metric is u_i = e_m_i / p_i, correct for preemptive EDF.

Phase 1b — Refine mapping (v5a / v5b only)

SPS balances load, not value. If high-utility tasks pile onto one core, timing blocks their optional segments even when energy is plentiful. Phase 1b rebalances utility density:

ud(i) = u_i * (cum[i][N_seg] - cum[i][0]) / p_i
UD(x) = sum of ud(i) over jobs mapped to processor x

A swap is accepted only when all three hold:

  1. UD imbalance strictly decreases;
  2. mandatory-utilisation imbalance does not worsen — disturbing SPS's load balance steals timing slack from Phase 5 even when DBF still passes;
  3. mandatory-only DBF at f_max stays feasible on both processors.

2a = linear doublet scan over pairs sorted by ascending |ud_a - ud_b|. 2b = one-swap-one-scan: fix the highest-UD processor pair, swap its first eligible pair, re-scan.

This is now the dominant error source at tight budgets. SPS (and this refinement) balance on utilisation at f_max. When the budget forces slow execution, effective times inflate 1.5–2.5× and a partition balanced for f_max is badly balanced for the operating point actually used. Neither step is energy-budget-aware.

Phase 1b′ — Budget-aware refine (v6)

Phase 1b always balances utility density. Measured against optimal ILP mappings that is right only when energy is plentiful — the optimum concentrates when energy binds:

rho    SPS UD-spread   OPT UD-spread   optimum...
0.4        0.504           0.730       CONCENTRATES (3/4 instances)
0.7        0.472           0.511       neutral
1.0        0.472           0.295       BALANCES

The mechanism: with energy plentiful everything runs at f_max and the binding resource is per-processor time, so spreading optional work keeps any one core from saturating. With energy tight, utility per energy is u_i/g(f), so the budget should go to high-u_i work while low-value work runs slowly to shrink its energy footprint — and running slowly costs time on its own processor. Scattering low-value jobs makes every core pay that slowdown, including the cores hosting the valuable optional work; segregating them onto dedicated donor cores localises the penalty where nothing is lost.

Phase 1b′ therefore flips its objective on a parameter-free regime test:

energy-bound?  E_mand_fmax > B
  yes -> MAXIMISE  sum UD(x)^2     (concentrate)
  no  -> MINIMISE  sum UD(x)^2     (balance, as before)

Sum-of-squares is used in both directions because, for a fixed total, it rises exactly when mass concentrates and falls exactly when it spreads.

And it judges feasibility at the operating point. SPS checks utilisation ≤ 1 at f_max, but a tight budget forces execution at

f̂ = max{ f in F : E(W_mand, f) ≤ B }     W_mand = SUM N_job_i * e_m_i

where effective times inflate by 1/f̂ — so a mapping "feasible at f_max" can leave a core with almost no slack where it matters. Both the DBF guard and the load-balance guard use f̂. (On the ρ=0.4 instances this predicts f̂=0.6; the optimal solver used 0.6 on essentially every job.)

Guard. 1b′ optimises a proxy (utility density), so it can land on a mapping the full pipeline scores lower than plain SPS. Both are scored on the real objective and the better is kept — so the refinement cannot hurt. This guard was added after a first run regressed one instance (91.17 vs 108.89).

Phase 1c — Mapping local search (v6)

Best-improvement search over single-job reassignments. Every candidate mapping is scored by running the entire downstream pipeline (phases 2–6b) and reading the utility it actually achieves — the real objective, not a proxy like utility density.

for each round (max MAP_LS_ROUNDS = 2):
    for each job, for each other processor (max MAP_LS_MAX_MOVES = 24 candidates):
        trial = mapping with that one job moved
        u, feasible = full_pipeline(trial)
        keep the best strictly-improving trial
    stop when no move improves

Infeasible candidates are discarded and the incumbent is replaced only on strict improvement, so the result is never worse than the mapping handed in. Cost is O(rounds × moves × pipeline); at J=10–13 the full 90-instance sweep still runs in under 3 s, but MAP_LS_MAX_MOVES needs tuning as J grows.

Why Phase 1c is ~156× slower than Phase 1

Measured on the ρ=0.7 instances (J = 10–13 jobs, 2 processors):

Stagemean timewhat it evaluateshow many times
Phase 1 — Quantum SPS0.20 ms utilisation arithmetic, one pass per quantumonce
Phase 1b′ — budget-aware refine0.23 ms a proxy — the Δ of Σ UD(x)², a few float ops per candidate swap; DBF is touched only when a swap is accepted ~J² cheap candidates

So the slowdown is not that the search is complicated — it visits only J × (P−1) single-job moves per round, fewer candidates than Phase 1b′ considers. It is that the scoring function is ~5× more expensive than all of Phase 1, and it is called ~25 times instead of once:

Phase 1c   30.91 ms
  = ~25 evaluations x 1.11 ms per full pipeline   (28.7x one pipeline)
  = 156x Phase 1

The proxy-versus-truth trade

Phases 1 and 1b′ are fast because they never build a schedule. They optimise surrogates — utilisation balance and utility density — that are pure arithmetic on per-processor aggregates. Phase 1c deliberately abandons the surrogate: the only way to know what a mapping is worth is to schedule it. That is also precisely why it works where 1b′ alone does not (1b′ can land on a mapping the pipeline scores lower than plain SPS, which is why it needs a guard).

Where the pipeline's own 1.11 ms goes

One evaluation is itself a nest of loops, with DBF at the bottom:

Phase 1c
 └─ x25  full pipeline
     ├─ Phase 4   iterative scale-down, sorted candidates, DBF check per attempt
     ├─ Phase 5   multi-pass greedy: per pass, per job -> min_slack_for_job
     ├─ Phase 6   O(J^2) giver/receiver pairs, and every accepted swap
     │             RE-RUNS Phase 5 as a fill pass
     └─ Phase 6b  per round: shadow prices over all jobs, then Phase 5 AGAIN
                              ↓
                    min_slack_for_job / check_all_timing
                    each O(P . |A| . |D| . J)

Phase 5 is therefore executed many times inside a single "one pipeline" call — once directly, once per Phase 6 swap, and once per Phase 6b accepted trade. The DBF window scan is the innermost primitive and dominates.

How this scales — the real concern

total ~ rounds x min(J.(P-1), MAP_LS_MAX_MOVES) x pipeline(J)
                                                   ^ superlinear in J:
                                                     Phase 6 is O(J^2) and
                                                     |A|,|D| both grow with J

At J=13 this is 31 ms and invisible — the whole 90-instance sweep runs in under 3 s. But the move count grows as J·P and each evaluation gets superlinearly dearer, so the product grows fast. MAP_LS_MAX_MOVES = 24 caps the first factor, which bounds the runtime but means the search covers a shrinking fraction of the neighbourhood as J grows — on a large instance Phase 1c would examine 24 of potentially hundreds of possible moves.

If Phase 1c has to scale, the fix is a cheaper screen, not a smaller search. Options, cheapest first: (1) two-stage evaluation — rank candidates by the 1b′ proxy, then full-evaluate only the top handful; (2) restrict the move set to jobs on the most-loaded or highest-UD processor, where improvement is likeliest; (3) warm-start each evaluation from the incumbent schedule rather than rebuilding from k=0, f_max; (4) early abort a pipeline once its partial utility cannot beat the incumbent. None of these is needed at the current instance sizes, and none has been implemented.
Effect. These two stages are what heuristic_v6 adds to v5b. Mean gap versus the exact ILP falls 13.94% → 3.55% (median 0.15%, optimal on 25/50), which is better than ILP v2 (4.79%) — a pure heuristic beating SPS+exact-ILP, possible only because it improves the mapping that ILP v2 is structurally stuck with. At ρ=0.4 the gap drops 31.4% → 4.0%; at ρ≥0.8 it reaches 0.0%. Against v5b instance by instance: better on 34, equal on 16, worse on 0.

Phase 2 — Left shift (diagnostic)

start = max(proc_avail, release)   finish = start + e_eff(i,k,z)   slack = deadline - finish

Simulates non-preemptive EDF packing, but the real system is preemptive EDF, so this only estimates where idle time sits. Hard feasibility is always decided by DBF. Run once; its output is printed but gates nothing.

Phase 3 — Energy slack (terminal feasibility test)

Computes Δe = B - E_consumed at the current state. The terminal test is the part that was wrong until 21 August — see §8. It now compares the budget against a true lower bound rather than the f_max cost:

E_floor = SUM over jobs of  min over z of  E(cum[i][0], f_z)
if B < E_floor:   infeasible at ANY frequency   -> terminate
else:             continue to Phase 4 and let it scale

Ignoring timing only loosens the bound, so this is a sound necessary condition and can never wrongly reject a solvable instance.

Phase 4 — Aggressive frequency scaling

Steps frequencies down one level until the schedule fits the budget. Rules:

  • skip any step with no energy saving (E_new ≥ E_cur) — below f* slowing down costs energy;
  • revert the step if the DBF check fails;
  • stop the instant E_total ≤ B — this phase targets feasibility, not efficiency;
  • candidates are visited in order of energy saved per unit time cost (descending), not task index — index order can burn DBF slack on poor trades and then fail to reach the budget on instances that are in fact schedulable.

The phase is gated: if f_max already fits the budget it does nothing, because lowering frequency inflates effective times and would starve Phase 5 of timing slack.

Phase 5 — Greedy optional segments

The main utility engine. Jobs are visited in a stable order sorted by (-u_i, task_id, job_id); each outer pass adds at most one segment per job, and the outer loop repeats until nothing more can be added. Three cases, tried in order:

CaseConditionAction
(i) add outright min_slack ≥ add_time AND E_slack ≥ add_energy commit; nothing else disturbed
(ii.A) raise j*'s frequency timing blocks, energy available step j* up one level to shrink its execution time, then full check_all_timing
(ii.B) global energy donation energy blocks, timing available lower other jobs' frequencies to fund it — see below

Case ii.B was substantially widened on 22 August. Donors are drawn from all processors (energy is a global budget, so the old same-processor restriction was arbitrary), the old "donor must have lower utility rate" rule was removed (downshifting costs the donor zero utility, so it guarded a cost that does not exist), and several donors may contribute until the segment becomes affordable. Donors are ranked by time paid per unit energy freed; any donor at or below f* is skipped; all donors are reverted if the final DBF check fails.

Phase 6 — Best-first pairwise swap

  1. Search every (giver, receiver) pair — giver has ≥1 active segment, receiver has < N_seg. With the giver's last segment tentatively removed, require net = u_recv*e_recv_next - u_give*e_give_last > 0, the energy balance E_freed - E_cost ≤ E_slack, and the receiver's timing min_slack ≥ add_time.
  2. Execute the highest-net-gain swap; re-verify with full check_all_timing.
  3. Fill pass — re-run Phase 5 on whatever the swap freed.
  4. Repeat until no improving swap exists.

Swaps may cross processors, since energy is global: dropping a low-value segment on P0 can fund a high-value one on P1.

Phase 6b — Frequency↔segment trade (v5b / claudeoptimal)

Added 22 August. Two resources are scarce — energy (global) and time (per-processor DBF slack) — and frequency is the exchange rate between them. For a segment of work w on task i at frequency f the marginal rates are independent of w:

utility per ENERGY = u_i / g(f)        g(f) = alpha/f + beta*f^2
utility per TIME   = u_i * f

Shadow prices are read off the current solution each round — no tuned constants:

lambda = max u_i/g(f)  over segments blocked ONLY by energy
mu     = max u_i*f     over segments blocked ONLY by time

accept a downshift  iff  lambda * dE  >  mu * dT

Then Phase 5 is re-run to spend the freed energy. The phase keeps a best-so-far snapshot and restores it unless utility strictly improves, so it can never return a worse schedule than it was handed — the worst case is a no-op. It never crosses f* (requires dE > 0), and every move is DBF-verified.

Phase 7 — Double-giver swap (claudeoptimal)

Some receivers are too expensive for any single-giver swap. Phase 7 removes the last segment of two givers at once to open enough combined timing + energy room for one receiver. The giver pool is sorted by ascending marginal utility (cheapest destroyed first) and truncated to _MAX_DG_CANDIDATES = 20; without the cap the pair enumeration is O(n³).

Phase 8 — Iterated greedy (claudeoptimal)

Escapes optima no local move can reach. Each of _IG_ITERATIONS = 8 rounds:

  1. Score every active segment by utility per unit execution time: density = u_i*(cum[k]-cum[k-1]) / add_time, add_time = (cum[k]-cum[k-1])/f_z.
  2. Destroy the lowest-density _IG_DESTROY_FRAC = 33% — the segments occupying the most schedule for the least value.
  3. Reconstruct with Phase 5 then Phase 6.
  4. Accept only on strict utility improvement; otherwise restore the incumbent.
Bug fixed 22 August. Phase 8 snapshotted and rolled back seg_k but not freq_idx — even though the Phase 5 and Phase 6 calls inside its reconstruct step both mutate frequencies. A rejected round therefore left an inconsistent (seg_k, freq_idx) pair whose energy could exceed the budget. The defect was latent while case ii.B rarely moved frequencies; widening ii.B exposed it immediately (claudeoptimal feasibility fell 84 → 79 until freq_idx was restored too).

8 · The defect: Phase 3 tested feasibility at the wrong frequency

The original failures were not gradual degradation — they were all-or-nothing, and lined up exactly with one condition: does the mandatory workload fit the budget at f_max?

rho_0.5.py            B= 34.50   E_mand@f_max= 46.00   E_mand@cheapest= 22.04
                      fits at f_max? NO        fits at cheapest? YES

A feasible schedule plainly exists — the mandatory segments cost 22.04 at a lower frequency against a budget of 34.50, and the ILP finds exactly such a schedule. The heuristic never looked, because Phase 3 exited before Phase 4 could act:

Phase 3 : E_slack = B - E_consumed        # evaluated at f_max, k=0
          if E_slack < 0:
              return ... 0.0, E_init      # <-- terminal, gave up here

Phase 4 : lower frequencies for energy feasibility   # never reached
Phase 4 exists precisely to fix the condition Phase 3 treated as fatal. The energy model here is g(f) = α/f + βf², minimised at f* ≈ 0.42 — so running slower costs 0.55 per unit work versus 1.15 at f_max, roughly 2× cheaper. Testing the budget at f_max therefore rejects a large band of perfectly solvable instances.

The fix

The terminal test now compares the budget against a genuine lower bound — every job at its cheapest available frequency, ignoring timing:

E_floor = SUM over jobs of  min over z of  E(cum[i][0], f_z)
if B < E_floor:  infeasible at any frequency   # necessary condition, sound
else:            continue to Phase 4 and let it scale

Ignoring timing only loosens the bound, so it can never wrongly reject a solvable instance. If Phase 4 subsequently cannot reach feasibility (because timing blocks the scaling), the schedule comes back over budget and the runner flags it — which is what still happens on the two ρ=0.4/0.5 instances v5b misses. (phases/energy_slack.py::min_possible_energy; applied to all six solver variants.)

Why low optional utilisation looked worse

Before the fix, the heuristics failed at β=0.2 and 0.4 but succeeded at 0.6 and 0.8 — more optional work made instances easier. That followed directly from the budget definition B = ρ × E_full_fmax, whose denominator includes optional work. Mandatory-at-f_max fits only when

rho ≥ U_M / (U_M + U_O)

so shrinking the optional part shrinks the budget while leaving the mandatory cost unchanged: at β=0.2 the threshold is ≈0.83, above the ρ=0.7 used here; at β=0.8 it falls to ≈0.56 and passed. Post-fix the anomaly is gone — every β value now solves 5/5.

9 · What to take from this

  1. The heuristics are far more robust than the pre-fix numbers suggested. Their apparent schedulability collapse was an artifact of one mis-placed test, not the algorithm. claudeoptimal now matches the exact solver on feasibility across all 90 instances.
  2. The utility gap is real and is an energy-tightness effect. v5b sits ~4% below the exact optimum when energy is plentiful (ρ=1.0) and ~50–78% below it when energy binds (ρ≤0.6). The heuristics still do not trade frequency for optional segments globally — that is the open item, and it is separate from the bug fixed here.
  3. claudeoptimal dominates v5b everywhere, by 3–28 percentage points of gap. Since v5b is the current runner default and the offline baseline for the online phase, that choice should be revisited.
  4. The exact ILP is cheap at this scale (J=10–13, proven optimal in milliseconds), so the small tier is a sound optimality benchmark. The scalability case for the heuristics must be made on much larger instances.
  5. ILP v1 and ILP v2 track each other closely, so SPS mapping costs little here; the interesting gap is frequency/segment selection, not mapping.
