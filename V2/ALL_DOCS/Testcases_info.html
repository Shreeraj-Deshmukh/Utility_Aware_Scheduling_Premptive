1 · The two pipelines

GENERATE                              RUN
usrt/gen/           gen_testcases.py  usrt/runner/          run_models.py
  spec.py       ->  writes .py                adapters.py ->  reads manifest.csv
  primitives.py     instances +               runner.py       runs each model
  generate.py       manifest.csv                              writes results.csv
  emit.py
  sweeps.py

  TestSpec + seed  ->  (processors, tasks, B)  ->  solver  ->  {utility, energy, ...}

The two halves are deliberately decoupled: the generator only writes files, the runner only reads them. Nothing about a model leaks into generation, so the same instances can be replayed against any solver, now or later.

2 · Where test-cases live

Directory layout

<out>/<sweep>/manifest.csv          one row per generated instance
<out>/<sweep>/results.csv          written by the runner, beside the manifest
<out>/<sweep>/set00/<factor>_<value>.py
<out>/<sweep>/set01/...            one directory per replicate (seed)

Example:

dry_run_tc/
  rho/
    manifest.csv
    results.csv
    set00/  rho_0.3.py  rho_0.4.py  ...  rho_1.py
    set01/  ...

setNN = one replicate, i.e. one random draw of the task-set shape. <factor>_<value>.py = one configuration point within that replicate. For the rho sweep the task set is fixed within a set and only the budget changes, so a ρ-curve is a controlled experiment on one instance.

3 · The generator: design

The structure follows paper §VII.A and is a strict OFAT (one-factor-at-a-time) design:

  • System parameters are fixed across every test case.
  • Simulation parameters are swept one at a time, with every other parameter holding its default.
  • One value of one parameter = one configuration. Each configuration gets --sets (default 100) independently seeded test cases, so a data point is a mean over replicates rather than one lucky draw.
ModuleResponsibility
spec.pyTestSpec dataclass — every knob, plus validate() enforcing the locked constraints
primitives.pyUUniFast, 0.01-unit donation, harmonic periods, random frequency sets, normal segment split, ρ budget, feasibility guard
generate.pydraw_taskset(spec, seed) -> TaskSet
emit.pywrites the runnable .py + one manifest row
sweeps.pythe OFAT drivers and generate_all

4 · Knobs

Simulation parameters — these are what we vary

KnobPaperMeaningdefaultsweep grid
n_prcNprchomogeneous processors2 2, 4, 8, 16
n_tskNtskperiodic tasks8 4, 6, 8, 10, 12
u_mand_factorαU_M = α × N_prc — mandatory load, drives timing pressure0.5 0.1 … 0.9
u_opt_factorβU_O = β × (N_prc − U_M) — optional headroom0.50.1 … 0.9

Why β is defined against the remaining capacity. U_M + U_O = U_M + β(N_prc − U_M) ≤ N_prc for any β ≤ 1, so total utilisation can never exceed capacity — the cap holds by construction, with no extra guard and no hand-picked parameter bands.

Notation collision. The paper reuses α/β for both the energy model (§II) and the utilisation parameters (§VII.A). The code renames the utilisation ones to u_mand_factor / u_opt_factor so nothing is ambiguous.

5 · How one instance is built

draw_taskset(spec, seed):
  1. frequency set : 5 distinct levels from the 0.05 grid, f_max forced in
  2. periods       : base * 2^m, first tasks get distinct m so >=3 periods appear
  3. mandatory util: UUniFast over U_M, then DONATE excess above gamma in 0.01 units
  4. optional util : UUniFast over U_O, then donate above the per-task cap delta*u_mand_i
  5. exec times    : e_m = u_mand_i * p_i ;  optional split across N_seg segments by a
                     NORMAL draw (mean = U_opt_i*p_i / N_seg, sd = 20% of mean),
                     renormalised so the task total is preserved exactly
  6. utility       : u_i ~ U(1, 5)
  7. theta         : per-task ACET multiplier ~ U(xi, 1)          [paper VII.A.2(f)]

Why donation, not discard-and-redraw

The paper specifies that utilisation above a cap is iteratively donated to other tasks in units of 0.01. That preserves the shape of the UUniFast draw; discarding and redrawing until the cap happens to be satisfied biases the distribution toward flatter task sets. When the excess cannot be placed anywhere the paper says "report error" — the generator emits the instance but sets donate_ok=0 and prints a delta-cap UNMET line.

Feasibility guard

With guarantee_feasible (the default) the draw is repeated under perturbed seeds until the mandatory part packs onto n_prc cores by Worst-Fit-Decreasing (per-core utilisation ≤ 1, which is sufficient for partitioned preemptive EDF with implicit deadlines). The schedulability sweep turns this off on purpose, so the success-rate cliff can be measured.

Two documented OFAT deviations, both printed at generation time.
1. The n_prc sweep scales n_tsk (8→12→23 for 8→16 cores), because U_M = α·N_prc cannot fit in 8 tasks at γ=0.5. The realised n_tsk is recorded in the manifest.
2. The δ cap can be arithmetically impossible: satisfying it requires β ≤ 2α/(1−α), which at α=0.1 caps β at 0.222 — so the default β=0.5 cannot comply. Those instances get donate_ok=0.

7 · What a test-case file looks like

Every instance is a standalone, runnable Python module exposing testcase(), so it loads through the same load_testcase() path as the hand-written testcase.py. It carries its own provenance.

"""Auto-generated USRT testcase -- DO NOT EDIT BY HAND.
Provenance:
{"B": 96.6, "H": 80, "J": 24, "factor": "n_tsk", "n_frq": 5, "n_prc": 2, "n_tsk": 6,
 "rho": 0.7, "seed": 1000, "set": 0, "sweep": "n_tsk", "u_mand_factor": 0.5,
 "u_opt_factor": 0.5, "value": "6", "xi": 0.6}
"""
_SPEC = '{...same dict...}'

def testcase():
    processors = [
        {'id': 0, 'frequencies': [0.35, 0.6, 0.8, 0.9, 1.0]},
        {'id': 1, 'frequencies': [0.35, 0.6, 0.8, 0.9, 1.0]},
    ]
    tasks = [
        {'id': 0, 'e_m': 3.019356, 'e_o_k': [0.649871, 0.484970],
         'p_i': 10, 'u_i': 2.9499, 'theta': 0.7846},
        ...
    ]
    B_BUDGET = 96.600000
    return processors, tasks, B_BUDGET

theta is the per-task ACET multiplier. Offline solvers ignore the extra key; the online simulator reads it, which is what makes an online run reproducible from the file alone rather than from a simulator setting.

8 · The runner: how instances reach the models

run_models.py <manifest.csv | sweep_dir | testcases_root> [--models ...] [--heur ...]

for each row in manifest.csv:
    path = resolve(row['file'])
    processors, tasks, B = load_testcase(path)      # same loader as run.py
    for each model:
        metrics = run_model(model, processors, tasks, B, ...)
        write {**row, **metrics} -> results.csv

Models available

--modelsWhat it isGurobi
ilp_v1exact ILP — joint processor + frequency + segment. The optimality benchmark.yes
ilp_v2SPS mapping + exact ILP for frequency/segments. The ceiling for any SPS-based heuristic.yes
heuristicthe staged pipeline; pick the variant with --heur (v3 v4 v5a v5b v6 claudeoptimal)no
greedy_sps_baselinenaive floor — SPS only, f_max pinned, greedy segmentsno

What the adapters do

ConcernHandling
Solver chatterTwo-layer suppression: fd-level dup2 to devnull (captures Gurobi's C log) and a sys.stdout swap (captures Python prints and makes them encoding-proof, so box-drawing glyphs cannot crash a cp1252 console)
ILP timeoutGurobi TimeLimit; returns the best incumbent as time_limit, or timeout if none was found. Bounds the solve, not model building
Infeasible ILPscomputeIIS/write monkeypatched to no-ops — they are slow and litter .ilp files
Energy model consistencyILP v1's module-globals are re-pointed to usrt.models at runtime, and every model's energy is recomputed through usrt.models, so all models are scored on one energy model
Heuristic validationthe returned schedule is checked against the budget; over-budget results are recorded infeasible rather than counted as successes
Errorscaught per (instance, model) and written as a status=error row, so one bad instance never aborts a sweep
Resumecompleted (file, model) pairs are skipped; Ctrl-C and restart is safe
Schema driftappending under a mismatched results.csv header raises instead of silently misaligning rows

9 · Metrics collected

MetricMeaning
utilitytotal optional utility — the objective
energyschedule energy, recomputed via usrt.models for all models
util_per_energyutility ÷ energy — energy efficiency
model_feasibledid this model produce a valid schedule (1/0) — aggregated over a configuration this is the success rate
runtimewall-clock seconds — scalability
gapMIP relative gap (ILP only)
statusoptimal | solved | time_limit | timeout | infeasible | error

Derived after the fact, by joining on file:

  • optimality gap = (utility[ilp_v1] − utility[model]) / utility[ilp_v1]
  • mapping vs heuristic decomposition — compare against ilp_v2 instead of ilp_v1 to separate "cost of the SPS mapping" from "cost of the heuristic search"
  • success rate = mean model_feasible over a configuration

10 · Schemas

manifest.csv — 24 columns, one row per instance

file, sweep, set, factor, value,
n_prc, n_tsk, n_frq, u_mand_factor, u_opt_factor, rho, xi,
U_M, U_O, B, H, J,
e_mand_fmax, e_full_fmax, e_mand_min,
feasible, donate_ok, seed, redraws
ColumnMeaning
factor, valuewhich knob this instance varies, and to what — the x-axis of any plot
U_M, U_Orealised total mandatory / optional utilisation
H, Jhyper-period and job count (J drives ILP size)
e_mand_fmaxmandatory energy at f_max — if > B the instance is energy-bound and DVFS is mandatory
e_mand_minmandatory energy at the cheapest frequency — B < e_mand_min is provably infeasible
feasibleinstance property: does the mandatory part pack at all
donate_ok0 when the δ cap could not be met
seed, redrawsfull provenance — regenerates bit-identically

results.csv — manifest columns + 9 metric columns

... 24 manifest columns ...,
model, status, model_feasible, utility, energy, util_per_energy, runtime, gap, error
feasible vs model_feasible are different and both matter. feasible is the generator's verdict (can the mandatory part be packed at all); model_feasible is this model's verdict. The pair separates "the instance is impossible" from "this model's partitioning failed" — the row feasible=1, model_feasible=0 is exactly the partitioning-limitation story. They were originally the same column name, and the model's value silently overwrote the generator's until they were renamed.

11 · End-to-end workflow

# 1. generate
python gen_testcases.py all --sets 100 --out testcases

# 2. run the cheap models everywhere
python run_models.py testcases/ --models ilp_v2,heuristic --heur v6

# 3. add the exact benchmark on the ILP-tractable sweeps only
python run_models.py testcases/n_tsk/manifest.csv --models ilp_v1 --time-limit 60

# 4. add the naive floor for a lower reference
python run_models.py testcases/ --models greedy_sps_baseline

# 5. results land beside each manifest
#    testcases/<sweep>/results.csv   -- join to manifest on 'file'

Small, ILP-tractable batch (what the 21/22 Aug docs used — H=40, J=10–13, 90 instances):

python gen_testcases.py rho --sets 5 --n-prc 2 --n-tsk 5 --kmax 2 --max-seg 3 \
       --n-frq 5 --grid 0.3,0.4,0.5,0.6,0.7,0.8,0.9,1.0 --out dry_run_tc
python run_models.py dry_run_tc --models ilp_v1,ilp_v2,heuristic --heur v6 --time-limit 20

12 · Gotchas & known issues

IssueDetail
Stale testcases/18,500 instances from the pre-§VII.A generator. Old schema and old definitions — regenerate before use (§2).
ILP.py constantshard-codes ALPHA=1.0, BETA=0.5. The runner re-points them, but standalone python ILP.py solves the wrong energy model. One-line fix: import from usrt.models.
heuristic_v1returns a ScheduleState, not the 4-tuple every other variant returns — unusable through the runner (produces an error row). Works via run.py.
Schema changesafter changing manifest or metric columns, delete the old results.csv; the runner refuses to append under a mismatched header.
Regenerating with fewer --setsleaves stale .py files on disk. The manifest is the source of truth and ignores them.
Gurobi licenceexpires 2026-08-19; both ILPs stop working after that. Heuristics and the online phase are unaffected.
Online phasenot in the runner. Generated theta makes online runs reproducible, but no online adapter exists yet — its result is a distribution over the ACET realisation, not one number per instance.
