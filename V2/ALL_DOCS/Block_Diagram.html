00 — How to read this

Colour carries meaning, not decoration

The four hues map onto the four things this project keeps separate. Two of them are the problem's own scarce resources: time slack is per-processor (a DBF window property) and energy is one global budget. Any block that touches one of those is coloured for it.

Shared substrate Four modules sit under every path and are drawn only once, in the system map: usrt/models.py (α=0.15, β=1.0, energy_val, e_eff_val), usrt/utils.py (lcm_list, build_cum, build_job_times), usrt/dbf/ (window_slack, min_slack_for_job, check_all_timing) and usrt/output.py (print_schedule).

01 — Where every number comes from

Three origins, and only one of them is the test case

Before any pipeline runs, an instance is assembled from three separate places. Mixing them up is the easiest way to misread a result — e_m varies per test case, ALPHA never does, and h is not stored anywhere at all.

Why these two are special They are the only physical parameters in the project, and they are deliberately excluded from every sweep — changing them changes the machine, not the workload. models.py is the single source of truth; ILP.py imports from it rather than declaring its own (it hard-coded a stale 1.0 / 0.5 until 22 Aug, silently solving a different problem). Under α=1.0, β=0.5 the optimum sits exactly at f_max and DVFS is degenerate — which is why so many older documents describe frequency scaling as a no-op.

02 — System map

Two entry points, four solver paths, one substrate

run.py runs one instance interactively and prints a full schedule. run_models.py runs a whole sweep silently and writes CSV. Both funnel into the same run(processors, tasks, B) contract that every solver implements.

python run.py testcase.py heuristic_v7 # one instance, full printout python run_models.py dry_run_tc --models heuristic --heur v7
03 — Exact solvers

ILP v1 and v2 differ by exactly one decision

v1 lets Gurobi choose the processor too, so its variable carries an x index and its DBF constraints range over every job's arrival/deadline set. v2 fixes the mapping with SPS first, which drops x from the variable and shrinks each DBF constraint to one processor's own windows. That is the whole difference — and it is also v2's ceiling: it can never repair a bad mapping.

04 — Heuristic

One mapping stage that varies, one phase spine that doesn't

Every heuristic variant is the same downstream pipeline bolted onto a different mapping strategy. That is the single most useful thing to hold in your head: v3 through v7 differ almost entirely in Phase 1. Phases 2–6b are shared modules called with the same arguments in the same order.

05 — Online

Precompute per processor, then spend windfalls at runtime

The online phase does not schedule anything. It takes a finished offline schedule and, whenever a job finishes early, decides how to spend the freed time and energy on downstream jobs. Time slack stays on its own processor; energy goes into one shared pool every processor draws from.

06 — Experiment harness

The generator only writes; the runner only reads

The two halves never import each other. Nothing about a model leaks into generation, so the same instances can be replayed against any solver, now or later. The handshake between them is two files on disk: a directory of runnable .py test-cases, and a manifest.csv that describes them.

python gen_testcases.py all --sets 100 --out testcases python run_models.py testcases/ --models ilp_v1,ilp_v2,heuristic --heur v7 # resume is on by default — safe to interrupt and restart
