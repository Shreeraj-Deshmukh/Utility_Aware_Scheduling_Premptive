End-to-End Run Pipeline

How a result is produced from nothing: which files generate test cases, where they land, how solvers consume them, where results are written, and how figures are drawn. Written so a reader with no prior exposure to this tree can reproduce the experiments on a fresh machine.

Last verified against the live tree: 13 September 2026. Every path, flag and constant below was read from the code, not from memory.

1 · Quick start

From V2/, with Gurobi licensed and matplotlib installed:

# 1. GENERATE  -- one OFAT sweep, 100 test cases per configuration
python gen_testcases.py rho --sets 100 --out tc_demo

# 2. RUN       -- every solver over that batch
python run_models.py tc_demo --models ilp_v1,ilp_v2,ilp_v3,ilp_v4 --time-limit 60
python run_models.py tc_demo --models greedy_sps_baseline
for h in v3 v4 v5a v5b v6 v7 claudeoptimal; do
    python run_models.py tc_demo --models heuristic --heur $h
done

# 3. INSPECT   -- results land beside each manifest
#    tc_demo/rho/manifest.csv      (what was generated)
#    tc_demo/rho/results.csv       (what each solver achieved)

PowerShell equivalent for the loop:

foreach ($h in 'v3','v4','v5a','v5b','v6','v7','claudeoptimal') {
    python run_models.py tc_demo --models heuristic --heur $h
}
For runtime measurements use run_timed.py instead. run_models.py times each solve once, and a single measurement was observed to be wrong by 97× (a 0.27 s solve recorded as 90.7 s when the OS descheduled the process). run_timed.py takes the best of N repeats and marks time-limit censoring explicitly. Use it for any claim about speed; run_models.py is fine for utility only.

2 · The three stages

  STAGE 1 — GENERATE                STAGE 2 — RUN                 STAGE 3 — FIGURES
  ──────────────────                ─────────────                 ─────────────────
  gen_testcases.py                  run_models.py   (utility)     make_figures.py
      │                             run_timed.py    (timing)           │
      ▼                             run.py          (one instance)     ▼
  usrt/gen/                             │                         ALL_DOCS/figures/
    spec.py      knobs                  ▼                           *.pdf  (vector)
    primitives.py  UUniFast, periods  usrt/runner/
    generate.py  draw one task set      runner.py   loop + resume
    emit.py      write .py + manifest   adapters.py normalise metrics
    sweeps.py    OFAT drivers               │
      │                                     ▼
      ▼                                 usrt/solvers/*.py
  tc_<name>/<sweep>/setNN/*.py         ILP.py  (ilp_v1, repo root)
  tc_<name>/<sweep>/manifest.csv           │
                                            ▼
                                    tc_<name>/<sweep>/results.csv

The halves are deliberately decoupled: the generator only writes, the runner only reads. No solver detail leaks into generation, so the same instances can be replayed against any solver, now or later.

3 · Stage 1 — generating test cases

Entry point

python gen_testcases.py <sweep> [options]
FileResponsibility
gen_testcases.pyCLI. Parses flags, builds a TestSpec, calls a sweep driver.
usrt/gen/spec.pyAll knobs live here as the TestSpec dataclass, plus validate().
usrt/gen/primitives.pyUUniFast, the 0.01-unit donation, harmonic periods, random frequency sets, normal segment split, ρ budget, feasibility guard.
usrt/gen/generate.pydraw_taskset(spec, seed) — produces one instance.
usrt/gen/emit.pyWrites the runnable .py file and one manifest.csv row.
usrt/gen/sweeps.pyThe OFAT drivers and the factor grids.

The sweeps (one factor at a time)

A configuration is one value of one factor with every other parameter at its default. Each configuration gets --sets independently seeded instances.

Sweep nameDefault grid (usrt/gen/sweeps.py)Studies
n_prc2, 4, 8, 16processor count
n_tsk4, 6, 8, 10, 12task count / problem size
n_frq2, 3, 5, 8, 12number of DVFS levels
u_mand_factor0.1 … 0.9α — mandatory load (timing pressure)
u_opt_factor0.1 … 0.9β — optional headroom
rho0.2 … 1.0ρ — energy budget (energy pressure)
xi0.3 … 0.9ξ — ACET spread (online only)
allevery factor abovefull OFAT suite
util_gridα × β 2-Djoint utilisation (NOT one-factor-at-a-time)
schedulabilityα past capacitysuccess-rate cliff (feasibility guard OFF)

Command-line overrides

--sets N        test cases per configuration (paper uses 100)
--seed N        base seed (default 1000); set+seed makes runs reproducible
--out DIR       output root                     --grid a,b,c   override the factor's grid
--n-prc N       processors                      --n-tsk N      tasks
--alpha F       u_mand_factor  (NOT energy alpha -- see §8)
--beta  F       u_opt_factor   (NOT energy beta  -- see §8)
--rho F         energy budget fraction          --xi F         ACET multiplier floor
--n-frq N       DVFS levels                     --max-seg N    max optional segments
--kmax N        periods = base * 2^m, m in 0..kmax  (controls hyper-period H, hence J)
--base-per N    base period
To change J (job count) independently of task count, use --kmax. Periods are base × 2^m, so H = base·2^kmax and J = Σ H/p_i. Raising --kmax raises J at fixed --n-tsk — the only way to separate those two variables, which are otherwise ~98% correlated.

4 · Where test cases are stored

<out>/<sweep>/manifest.csv              one row per instance — the index
<out>/<sweep>/results.csv               written later by run_models.py
<out>/<sweep>/results_timed.csv         written later by run_timed.py
<out>/<sweep>/set00/<factor>_<value>.py    ← the instances
<out>/<sweep>/set01/ ...                   one directory per replicate (seed)

Concretely:

tc_demo/rho/manifest.csv
tc_demo/rho/set00/rho_0.3.py   rho_0.4.py  ...  rho_1.py
tc_demo/rho/set01/rho_0.3.py   ...

setNN = one replicate (one random draw of the task-set shape). <factor>_<value>.py = one configuration point within it. In the rho sweep the task set is fixed within a set and only the budget changes, so a ρ-curve is a controlled experiment on one task set.

What one instance file contains

"""Auto-generated USRT testcase -- DO NOT EDIT BY HAND.
Provenance: {"B": 96.6, "H": 80, "J": 24, "factor": "rho", "n_prc": 2, ... "seed": 1000}
"""
def testcase():
    processors = [{'id': 0, 'frequencies': [0.35, 0.6, 0.8, 0.9, 1.0]}, ...]
    tasks = [{'id': 0, 'e_m': 3.019, 'e_o_k': [0.649, 0.484],
              'p_i': 10, 'u_i': 2.9499, 'theta': 0.7846}, ...]
    B_BUDGET = 96.600000
    return processors, tasks, B_BUDGET

Each file is standalone and runnable, and carries its own provenance in the docstring, so any instance can be regenerated from (TestSpec, seed). theta is the per-task ACET multiplier used by the online phase; offline solvers ignore it.

Generated data is gitignored. tc_*/ directories are excluded by .gitignore because every instance is regenerable from its provenance. Ship the code and the commands, not the batches.

5 · Stage 2 — running solvers

Three entry points, different jobs

ScriptScopeUse for
run.pyONE instance, verbose console outputdebugging a single case, seeing phase-by-phase output
run_models.pyA whole batch → results.csvutility / feasibility at scale
run_timed.pyA whole batch, best-of-N → results_timed.csvany runtime claim

How a batch run works

for each row in manifest.csv:
    path = resolve(row['file'])
    processors, tasks, B = load_testcase(path)     # usrt/utils.py
    for each model:
        metrics = run_model(model, processors, tasks, B, ...)   # usrt/runner/adapters.py
        write {**row, **metrics} -> results.csv

So solvers pick up test cases sequentially, driven by manifest.csv — the manifest is the authoritative index, not the directory listing. Stray .py files left by an earlier, larger generation are ignored.

Available models

--models valueImplementationWhat it isGurobi
ilp_v1ILP.py (repo root)Exact: joint mapping + frequency + segments. The optimality reference.yes
ilp_v2usrt/solvers/ilp_v2.pySPS mapping + exact frequency/segmentsyes
ilp_v3usrt/solvers/ilp_v3.pyPredicted-work SPS mapping + same ILPyes
ilp_v4usrt/solvers/ilp_v4.pyheuristic v6's mapping search + same ILPyes

Runner options

run_models.py <dir|manifest.csv>  --models a,b,c  --heur v6  --time-limit 60
run_timed.py  <dir|manifest.csv>  --models a,b,c  --heur v6  --time-limit 300 \
                                  --repeats 3  --repeat-cutoff 20  --out results_timed.csv

Both are resume-safe: a completed (file, model) pair is skipped, so Ctrl-C and restart is harmless. Both refuse to append under a mismatched header (delete the results file after changing the schema).

What the adapter layer does

usrt/runner/adapters.py normalises every solver to one metrics dict and handles:

ConcernHandling
Solver console noisefd-level redirect (Gurobi's C log) + sys.stdout swap (encoding-proof)
ILP timeoutGurobi TimeLimit; returns best incumbent as time_limit, or timeout if none
Energy-model consistencyevery model's energy recomputed through usrt/models.py, so all are scored identically
Heuristic validationschedule re-checked against the budget; over-budget results recorded infeasible, utility discarded
Errorscaught per (instance, model) → a status=error row; one bad instance never aborts a sweep
Do not run two runners over the same batch at once. There is no file locking. Concurrent writers produced 4,046 duplicate and 7 malformed rows in one campaign before it was caught. One runner per batch directory.

6 · Where results are stored

Beside the manifest that produced them: <out>/<sweep>/results.csv. Every manifest column is copied onto every result row, so results are self-describing and need no join.

manifest.csv — 24 columns

file, sweep, set, factor, value,
n_prc, n_tsk, n_frq, u_mand_factor, u_opt_factor, rho, xi,
U_M, U_O, B, H, J, e_mand_fmax, e_full_fmax, e_mand_min,
feasible, donate_ok, seed, redraws

results.csv — those 24 + 9 metrics

model, status, model_feasible, utility, energy, util_per_energy, runtime, gap, error

results_timed.csv — those 33 + 5 timing columns

runtime_best, runtime_worst, repeats, censored, nondeterministic
ColumnMeaning
feasibleinstance property from the generator: can the mandatory part be packed at all
model_feasiblethis model's verdict. feasible=1, model_feasible=0 = solvable instance, this solver failed. Set to 0 on three distinct grounds, told apart by error: the mandatory part does not pack (empty error, checked before the solver runs); over budget: E=… (C3); or C2: committed schedule misses a deadline — a DBF re-check of the schedule the solver actually returned, added 13 Sep 2026. The last one has never fired on a real run (0 in 6300), but it is what makes the column trustworthy rather than merely plausible
utilitytotal optional utility — the objective. Empty when infeasible (discarded, not recorded)
censored1 = hit the time limit; the runtime is a LOWER BOUND. Exclude from runtime statistics
nondeterministic1 = repeats disagreed on utility. Should always be 0

Derived afterwards by joining on file: optimality gap (u[ilp_v1] − u[model]) / u[ilp_v1]; success rate = mean model_feasible.

8 · Tuning knobs — which file to edit

α and β mean two different things in this project. The energy pair lives in usrt/models.py and is never swept. The utilisation pair is u_mand_factor/u_opt_factor in spec.py and IS swept (and is what --alpha/--beta set on the command line). The paper reuses the same two letters for both; the code renames them to keep them apart.

A — Energy model constants: usrt/models.py

ALPHA = 0.15      # line 19
BETA  = 1.0       # line 20

E = ALPHA*(sum e / f) + BETA*f^2*(sum e)
g(f) = ALPHA/f + BETA*f^2      energy per unit work, minimised at f* = (ALPHA/2BETA)^(1/3)
With 0.15 / 1.0:  f* ~= 0.42, g(0.4)=0.535 vs g(1.0)=1.150  -> 2.15x cheaper below f_max

This is the single source of truth; all seven solver files import from here. Changing it changes every result but does not require regenerating test cases — the instance files do not encode the energy model.

One coupling to know. B_BUDGET = ρ · E_full_fmax and E_full_fmax = (α+β)·H·(U_M+U_O) uses the energy α+β. So if you change models.py, every stored B_BUDGET silently stops corresponding to its intended ρ. Regenerate the batches after an energy-constant change.

9 · What is NOT built yet

Stated plainly so nothing is assumed to exist.

1. There is no single end-to-end script. Nothing chains generate → run → figures. Today that is three commands plus a shell loop over the seven heuristic variants. Proposed: run_all.py --out DIR --sets N [--timed] that calls the three stages in order, with a single --models list and one progress line per stage. Roughly 60 lines; nothing blocks it.
2. run.py cannot run ilp_v1 or ilp_v4. Verified: its solver registry contains ilp_v2, ilp_v3, the heuristics, the baseline and online — but zero references to ilp_v1 or ilp_v4. Both work fine through run_models.py / run_timed.py, which use adapters.py (whose MODELS tuple does list all four). So single-instance debugging of those two models is not possible today. Fix: two lines in run.py's registry.
3. make_figures.py is not parameterised. Hard-codes three batch directory names and the filename results.csv. It cannot plot a new batch, and cannot plot results_timed.csv (the timing-grade data), without editing the source. Fix: add --batch and --results arguments.
4. The online phase has no batch runner. usrt/solvers/online_demo.py runs through run.py online for a single instance only. Generated instances already carry per-task theta, so online runs are reproducible — but there is no adapter, so the online phase has no sweep-scale evidence. The open design question is that its result is a distribution over the ACET realisation, not one number per instance.
5. No file locking in the runners. Running two runners over one batch corrupts results.csv (observed: 4,046 duplicate + 7 malformed rows). There is a schema guard but no lock. Fix: a lockfile per batch directory, or a per-model output file.
6. No automated test suite. Four separate defects this year were found only by accident, each of which a property test would have caught immediately: order-independence, energy ≤ B on every returned schedule, DBF feasibility, and each phase being non-regressive. Proposed: ~150 lines in tests/.

Only two third-party packages are actually required: gurobipy and matplotlib. Everything else in usrt/ is standard library. The heuristics and the generator run with no third-party packages at all — Gurobi is needed only for the ILP models, matplotlib only for figures.

pip install gurobipy matplotlib

Gurobi licence

The ILP models need a licence. An academic named-user licence is free.

grbgetkey <your-key>            # installs gurobi.lic
python -c "import gurobipy; gurobipy.Model()"   # should print the licence banner

Current licence on the development machine: LICENSEID 2853854, academic, valid to 2027-08-16. A new machine needs its own key. Without it, the four ILP models fail; all seven heuristics and the baseline still run.

Running without Gurobi

python run_models.py tc_demo --models greedy_sps_baseline
for h in v3 v4 v5a v5b v6 v7 claudeoptimal; do
    python run_models.py tc_demo --models heuristic --heur $h
done

This yields relative comparisons between heuristics but no optimality gaps, since those are measured against ilp_v1.

11 · Known caveats

CaveatDetail
SPS mapping bypassquantum.py places a large share of jobs by a min-utilisation fallback rather than by SPS proper (capacity is never released between quanta). Any claim of the form “the SPS mapping causes X” should be re-verified. Tracked in ALL_DOCS/ISSUES.md.
Stored results go staleResults embed no code version. When a shared file (quantum.py, packers.py, models.py) changes, every stored results.csv silently predates it. Re-run all models together after any change to shared code, never mix old and new rows.
v3, v4, v5a lack Phase 6bTheir columns conflate a mapping change with a missing phase, so they are not directly comparable with v5b/v6/v7.
δ cap can be impossibleSatisfying it needs β ≤ 2α/(1−α), so at α=0.1–0.2 the default β=0.5 cannot comply. Those instances carry donate_ok=0 and the generator prints a warning.
n_prc sweep co-varies n_tskU_M = α·N_prc cannot fit a fixed task count, so n_tsk scales 8→12→23. The realised value is in the manifest, so it is visible rather than hidden — but that row is “effect of cores with a proportionally larger task set”.
J and n_tsk are ~98% correlatedIn the default grids, J ≈ 2.3·n_tsk. Use --kmax to vary J at fixed n_tsk if you need them separated.
Timing needs repeatsA single measurement was observed wrong by 97×. Use run_timed.py for any speed claim, and exclude censored=1 rows from runtime statistics.
