A · Correctness & infrastructure

A1critical  ILP.py hard-codes the wrong energy constants

NOT IN CODEBASE · 4 Sep 2026Fixed 22 Aug. ILP.py imports ALPHA/BETA from usrt.models and carries a comment recording the old stale pair. Standalone runs are now correct.

ILP.py lines 51–52 set ALPHA = 1.0, BETA = 0.5. The project uses ALPHA = 0.15, BETA = 1.0 from usrt/models.py. Under the stale pair the energy-optimal frequency is fmax; under the real pair it is f* ≈ 0.42 — so the two models disagree about the entire DVFS story, not by a small margin.

Verified 22 Aug:  grep "^ALPHA = 1.0" ILP.py  ->  still present

Why it is critical rather than high: it fails silently. The runner re-points these globals at import time, so all measured results in the 21/22 Aug docs are valid. But a standalone python ILP.py testcase.py produces a plausible-looking optimum for a different problem, with nothing to indicate it. Two docs (V2_Commands_Reference, Testcases_info) show that exact command.

Fix: replace both lines with from usrt.models import ALPHA, BETA.

A2high  testcases/ was built by the superseded generator

NOT IN CODEBASE · 4 Sep 2026Resolved. The tree was deleted. Live batches: dry_run_tc/ (90 instances, 3 manifests, 3 results), tc_smoke/, baseline_22aug/.

18,500 instances across 9 sweep directories, all pre-dating the paper-§VII.A alignment. Their manifests still carry regime, util_per_core, opt_ratio, and the old sweep names (energy_rho, util_split, util_success).

The instances were generated under the old definitions: U_O = opt_ratio × U_M (not β(N_prc − U_M)), an affine ρ (not ρ × E_full_fmax), geometric segment shaping (not normal), and no per-task theta. They are not comparable with anything produced today.

The runner will happily consume them — it only requires a file column — so nothing errors; the results would simply describe a different experiment. Fix: regenerate or delete. It is also the largest artefact in the repo.

B · Experiment validity (all four found by code scan)

B1medium  v5a and v5b are no longer a controlled comparison

The version matrix describes v5a and v5b as siblings differing only in Refine-Mapping strategy (2a linear-doublet-scan vs 2b one-swap-one-scan). That is no longer true:

heuristic_v5a   freq_trade references: 0
heuristic_v5b   freq_trade references: 1

Phase 6b was added to v5b but not v5a, so they now differ by two things. Any measured v5a vs v5b difference can no longer be attributed to the refine strategy — which was the entire purpose of having both. Fix: add Phase 6b to v5a, or state plainly that the comparison is retired.

B2medium  Phase 6b applied to only 3 of 6 heuristic variants

v5b, claudeoptimal and v6 have the frequency↔segment trade; v3, v4 and v5a do not. The lineup is meant to be a ladder where each step adds one capability, and this breaks that reading: v4 → v5a → v5b now mixes a mapping change and a phase addition. Deliberate or not, it should be explicit, because it affects how every cross-variant table is interpreted.

B3medium  online_demo no longer matches the "v5b pipeline" it claims

online_demo.py states in three places that it builds the offline schedule "with the v5b pipeline". It calls quantum_sps_mapping → refine_mapping_2b → aggressive → greedy → swap directly, and therefore has neither the Phase 3 feasibility fix nor Phase 6b.

Currently harmless, and verified so. Re-running the online phase on 22 Aug gives exactly the historical numbers — offline 227.328242, online +68.356614, final 295.684856, feasible, 0 denied. At B=400 the Phase 3 gate and Phase 6b are both no-ops, so the two pipelines coincide.

But it is latent. At a tight budget they diverge: online_demo would lack the Phase 3 protection (declaring infeasible where v5b succeeds) and Phase 6b's utility. Since the online-phase audit recommends reporting from an energy-binding budget, this will bite exactly when it is used as intended. Fix: have offline_schedule call the real v5b run(), or drop the "v5b" claim.

B4medium  heuristic_v1 is unusable through the runner

It returns a ScheduleState object rather than the (seg_k, freq_idx, utility, energy) tuple every other variant returns. The adapter unpacks four values, so --heur v1 yields a status=error row rather than results. It works via run.py, which ignores the return value. Fix: conform the return, or exclude it explicitly with a clear message instead of an error row.

C · Generator & scalability

C1medium  The δ cap can be arithmetically impossible

Holding every task to optional ≤ δ×mandatory requires

beta <= 2*alpha / (1 - alpha)      # alpha=0.1 -> beta <= 0.222

so the default β=0.5 cannot comply at α=0.1 or 0.2. The generator emits the instance, sets donate_ok=0, and prints a delta-cap UNMET line — the paper's own answer is "report error". This is a genuine tension between the paper's U_O formula and the per-task ratio cap, not an implementation slip. Decide: constrain the (α, β) grid, or relax δ and drop the constraint from the write-up.

C2low  The n_prc sweep co-varies n_tsk

U_M = α·N_prc grows with cores, so 8 tasks cannot carry a 16-core load at γ=0.5 (8×0.5 = 4.0 < 8.0). n_tsk scales 8→12→23, which is a documented, printed departure from strict OFAT. The realised value is in the manifest, so it is visible rather than hidden — but any "effect of processor count" claim is really "effect of processor count with a proportionally larger task set".

C3medium  Phase 1c cost, and what the move cap really does

Measured at J=10–13: Phase 1 = 0.20 ms, Phase 1b′ = 0.23 ms, one pipeline = 1.11 ms, Phase 1c = 30.91 ms (~25 full pipelines; 156× Phase 1). The search is not the cost — 1c examines fewer candidates than 1b′ — the scoring function is, because it builds a real schedule per candidate.

total ~ rounds x min(J.(P-1), MAP_LS_MAX_MOVES) x pipeline(J)
                                                  ^ superlinear in J

Invisible today (whole 90-instance sweep < 3 s). The concern is that MAP_LS_MAX_MOVES = 24 bounds runtime by shrinking neighbourhood coverage as J grows — on a large instance 1c would examine 24 of hundreds of moves, so v6's advantage should be expected to decay with size and must be re-measured, not extrapolated.

C4medium  The DBF hot spot is compilable — 56× available, bit-identical

Profiling puts almost the whole cost of every heuristic in one function:

window_slack        (usrt/dbf/slack.py:16)      ~87% of heuristic wall time
 └─ min_slack_for_job (slack.py:31)             96.7% of those calls
     └─ phase_optional_segments (greedy.py:26)  91% of those
        (called 97x per solve: 18 from _pipeline,
         79 RE-ENTERED from phase_swap_local_search)

That function is a tight numeric loop over floats — roughly 7.8 million inner iterations in a single solve — which is the worst case for CPython. Every + on two floats unboxes both operands, type-checks, and re-boxes the result; at that iteration count the interpreter overhead dominates the arithmetic entirely.

Measured: 56×, with identical output

numba is already installed here (0.67.0). Numba is a just-in-time compiler: decorating a function with @njit makes it compile to machine code through LLVM on first call, so the same Python source afterwards runs at roughly C speed. Compiling the original algorithm verbatim — no caching, no restructuring, the same nested A×D scan — measured:

31.307 us/call  ->  0.554 us/call   =  56.5x      (bit-identical result)
It is not a one-line decorator. Numba's nopython mode supports only a subset of Python. The DBF code keys its dictionaries on (i, j) job tuples, which numba cannot compile — those structures have to be flattened into numpy arrays first. That is real work. There is also a ~0.1–1 s compile cost on the first call, which matters when timing short runs.

Do the algorithmic fix first — it is cheaper and language-independent

A memoisation plus 2-D prefix-minimum rewrite measured 3.16× at n_tsk=26, also bit-identical, by doing 2.6× less arithmetic (11,149,958 → 4,293,657 summed terms; window constructions 611,866 → 34,714, a 17.6× drop). That is an algorithmic saving, not a compilation one, so it is available in any language and it compounds with numba rather than competing with it. min_slack_for_job currently rebuilds every window from scratch even though a single-job move changes only one job's seg_k.

What this will NOT fix — the Amdahl ceiling

Amdahl's law bounds the whole-program speedup by the part left un-optimised: with a fraction p of runtime in the hot spot, making it infinitely fast still caps the speedup at 1/(1−p). Applied to v7 at n_tsk=26:

v7 = 323.6 ms, DBF = 71%          -> zero-cost DBF floor:  323.6 x 0.29 = 93.8 ms
after the algorithmic fix:
v7 = 115.4 ms, DBF = 39.4%        -> zero-cost DBF floor:  115.4 x 0.606 = 69.9 ms
                                     BEST-ILP at n_tsk=26:                 36.7 ms
                                     -> still 1.9x SLOWER with a free hot spot
And the real problem is growth, not constant factors. Between n_tsk=4 and n_tsk=26, v7's runtime grows 13.2× while the best exact model grows only 4.0×. Amdahl and compilation both address constant factors; a worse growth rate is not a constant factor, so the gap widens with problem size however fast each step is made. Compiling the hot spot is worth doing — it is a free, verified, result-preserving speedup that helps every heuristic — but it does not by itself make the mapping-search heuristics competitive with the exact solvers at scale.

Related: C3 (Phase 1c's cost is the scorer, not the search) and G1 (mapping is the dominant error source). A single-job move perturbs exactly two processors, so the deeper win is incremental evaluation — not re-running the whole pipeline per candidate.

D · Online phase

D1medium  Online phase is absent from the runner

Generated test cases now carry per-task theta, so an online run is reproducible from the file alone — but no online adapter exists, so the online phase has no sweep-scale evidence at all, unlike every offline model. Its result is a distribution over the ACET realisation rather than one number, which is the design question to settle first (report a mean over seeds, or sweep ξ as its own factor).

D2medium  Scalar-Δt DP over-plans; the commit DBF trims

The DP distributes one scalar Δt across a whole downstream chain and uses the full deadline interval as the per-job cap, so it is an optimistic upper bound the dynamic DBF then trims. Measured at B=400: promised 72.90, committed 68.36 — 4.55 utility lost over one event. Graceful degradation already recovers most of it; the residual is the price of the scalar (vs per-window vector) time state.

D3low  Aggregate-states quantisation clips the exact frontier

The exact Pareto frontier reaches ~16,400 points per level; the cap-256 grid keeps ~229 — a ~70× clip at ~3.8 time × 2.0 energy per bucket. It is feasibility-safe (dropping options can only lower a reported value), so this is bounded sub-optimality, not a constraint risk. Worth a sensitivity sweep only if DVFS becomes a headline online result, since a coarse grid can bucket away precisely the low-req_e points Option 3 relies on.

D4low  Per-event DP rebuild dominates online runtime

on_completion fully rebuilds the affected processor's DP after every completion. It is correct and keeps later lookups exact, but it is the bulk of the ~77 s simulation. The paper's "Lazy DP" improvement targets exactly this.

E · Paper coverage

E1medium  Paper §V.B "Heur1.0/Baseline" is not implemented

The paper defines a 2-phase baseline — WFD-style mapping by decreasing utilisation, then a local search over eight operations with probabilistic acceptance (simulated annealing in all but name). Nothing in usrt/ has probabilistic acceptance or WFD mapping.

Two of its operations lie outside our design space: O7 (dec freq + inc optional segment) and the segment-decreasing moves. O7 is precisely the trade the heuristics lacked before 22 Aug, so the paper's own baseline might beat v5b in the energy-bound regime — worth measuring before any "we beat the baseline" claim. greedy_sps_baseline covers the no-DVFS floor but is not this algorithm.

E2low  α/β mean two different things in the paper

§II uses α, β for the energy model; §VII.A.2(c)(d) reuses them for utilisation parameters. Both appear in the same results discussion. The code sidesteps it (u_mand_factor/u_opt_factor), but the paper should rename one pair.

E3low  §VII.A.2(d)(i) wording

Inside the paragraph defining optional utilisation it reads "Distribute mandatory utilization to each task with UUniFast" — almost certainly meant to be "optional". The implementation assumes the latter.

G · Findings (not defects)

G1info  At tight ρ the mapping, not the search, is the dominant error

Decomposing the gap with ILP v2 (SPS mapping + exact frequency/segment choice):

ρILP v1ILP v2claudeoptimalgap from mappinggap from search
0.423.1912.9811.1344.0%14.2%
0.763.6858.5754.178.0%7.5%
1.066.0065.5865.580.6%0.0%

This is why v6 targets the mapping, and why a heuristic can beat ILP v2 (3.55% vs 4.79% mean gap): v6 improves the mapping that ILP v2 is structurally stuck with. Two consequences for the write-up: report gaps against both ILP v1 and ILP v2, since a single number conflates two error sources; and do not claim near-optimality versus ILP v1 at tight budgets for any SPS-based method — that ceiling is structural.

Related and measured: LP-relaxation-rounded mappings did not reliably beat SPS (better at ρ=0.4/0.7, worse at 0.5/1.0), so the LP is worth adopting as an evaluation bound, not as a mapping oracle.
