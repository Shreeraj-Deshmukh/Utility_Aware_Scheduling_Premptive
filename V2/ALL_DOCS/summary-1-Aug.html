1. The Problem in One Paragraph

Schedule periodic real-time tasks (harmonic periods, preemptive EDF, job-level mapping) on homogeneous processors with discrete DVFS frequencies. Each job has a mandatory segment (must finish by deadline) and several optional segments (each adds utility). Choose, per job, a processor, a frequency, and how many optional segments to run, so as to maximise total utility subject to (1) all deadlines met (DBF), (2) total energy ≤ budget B, (3) no migration / no mid-run frequency change / one job per core at a time.

2. The Four Approaches (paper → code)

The paper (§I.1) defines four approaches. Three are offline (compute the whole hyper-period schedule assuming worst-case execution time), one is online (react at runtime to early completions).

ApproachWhat it is (paper)ImplementationStatus
ILP v1 Pure discrete optimisation — one solve decides job→proc, frequency, and segments jointly. Optimal. ILP.py (legacy, standalone, needs Gurobi) ⚠️ legacy only
ILP v2 SPS decides the mapping, then an ILP decides frequency + optional segments for that mapping. usrt.solvers.ilp_v2 (needs Gurobi) ✅ modular
Heuristic Fast, solver-free: build the schedule stage-by-stage (mapping → frequency → segments). usrt.solvers.heuristic_v1 … v5b, claudeoptimal ✅ main focus
Online Use time + energy slack from early completion to run extra optional segments at runtime. usrt/online/ + usrt.solvers.online_demo ✅ built

Run any via python run.py testcase.py <approach> (e.g. ilp_v2, heuristic_v5b, online).

3. System & Energy Model

  • Processors: homogeneous, discrete frequencies normalised to f_max = 1. Testcase set: {0.3,0.4,…,1.0}.
  • Tasks: harmonic periods; job (i,j) released at (j−1)·p_i, deadline j·p_i; hyper-period h = lcm(p_i).
  • Segments: mandatory G_{i,0} + optional G_{i,k}; executing k implies all previous. Utility ∝ optional work × u_i.
  • Timing (C1/C2): preemptive-EDF feasibility via the Demand Bound Function — for every window [t1,t2], Σ effective time of contained jobs ≤ t2−t1.
  • Energy (C3): E(i,j,k,z) = α·(Σe / f_z) + β·f_z²·Σe ,   Σ over all jobs ≤ B
Current constants: α = 0.15, β = 1.0 (in usrt/models.py). This puts the energy-optimal frequency f* ≈ 0.42 inside the range, so DVFS is a live decision. The earlier α=1, β=0.5 made f* = f_max — frequency was degenerate (see §8).

4. The Heuristic — SPS Mapping, Refine Mapping, and the 8 Phases

"The Heuristic" is this staged pipeline (paper §V). Every phase is a separate module under usrt/phases/ or usrt/mapping/; the versions (§5) are different assemblies of the same building blocks. Phases 1–6 are the paper's heuristic; Phases 7–8 are extra local-search layers used only by heuristic_claudeoptimal.

Invariant at the start of Phase 2: every job sits at f_max with zero optional segments (seg_k = 0). Phases 4–8 exist to spend the energy and timing budget on turning that into utility. Utility only ever comes from optional segments; frequency is purely a time↔energy converter (paper Eq. 8 has no f term).

Phase 1 — Quantum SPS mapping ✓

Decides job → processor (mandatory work only, at f_max). Work proceeds one quantum at a time, where the quantum is gcd of all periods, so every job boundary falls on a quantum edge. Per quantum [q_start, q_end]:

  1. Collect newly-arrived jobs plus any leftover deferred from earlier quanta.
  2. Classify each as mandatory-now (d == q_end — must be placed) or deferrable (d > q_end).
  3. Pre-filter: if total utilisation exceeds remaining capacity, defer the latest-deadline deferrable jobs until it fits.
  4. Run DPS + SPS to produce a balanced assignment.
  5. Verify per-processor utilisation ≤ 1.0; if violated, defer more deferrables.
  6. Commit the assignment and update the running proc_util.

After every quantum is placed: a full mandatory-only DBF check at f_max, followed by greedy repair if any window fails. (mapping/quantum.py, dps_sps.py, repair.py)

What DPS and SPS actually are

The paper never defines them. §V says only "Obtain mapping with SPS" and §IV "First compute a mapping with SPS of jobs (mandatory segments only with maximum frequency)" — it is treated as known prior work, and DPS is not mentioned at all. The only reference is [1] Kumar, Mayank & Mondal, TPDS 2019. What follows is read off the code.

A PS ("partial solution", mapping/ps.py) is a complete m-way split of some subset of the jobs: loads[0..m-1] kept sorted descending, the matching job-sets, and gap = loads[0] − loads[-1]. That gap is the only quality measure in the algorithm.

  • DPS — "Determining Partial Solutions". Builds the starting set. Jobs arrive sorted descending by load (LPT order). Each job goes into the active PS with the largest gap, but only if job_load ≤ gap — i.e. only where it fits inside the existing hole. A job too big for every hole would overshoot and create imbalance, so it seeds a new PS instead.
  • SPS — "Sum Partial Solutions". Merges them. Repeatedly take the two largest-gap partial solutions and combine. The merge is the criss-cross: it pairs A's heaviest slot with B's lightest, A's second-heaviest with B's second-lightest, and so on (self.loads[j] + other.loads[m-1-j]), so each solution's imbalance cancels the other's.

Traced on quantum [0,10] of testcase.py: DPS produces three partial solutions with gaps [0.0623, 0.0256, 0.0717]; SPS merges the two largest (0.0717 with 0.0623) into a gap of 0.0094, then folds in the third for a final gap of 0.0162.

Structurally this is the multi-way largest-differencing method — Karmarkar–Karp generalised from 2-way to m-way partitioning. All three signatures are present: descending-order processing, largest-with-smallest pairing on merge, and always working the most-unbalanced pair first. That identification is from reading the code, not from the paper.

Note the load metric. DPS and SPS see only scalar loads — they know nothing about releases or deadlines, which is why the per-quantum capacity gate and the post-loop DBF check + repair both have to exist. The metric is e_m_i / p_i, task utilisation. That is the right measure over a whole hyper-period, but it is being applied inside a single quantum, where the dimensionally correct quantity is work against window length (e_m / quantum).

Caveat — verified 4 Sep 2026. The per-processor utilisation gate in steps 3 and 5 above is defective: proc_util is initialised once and never released, so it is a running sum of e_m/p_i over the whole hyper-period — one term per job — rather than a utilisation. Once it passes capacity, every later quantum bails out at MAND_OVERUTIL and its jobs are placed by a min-util fallback instead of by SPS: 73% of jobs on testcase.py, and 0–60% on generated instances depending on utilisation and hyper-period. Adding processors does not help — the over-count grows with m just as fast as capacity does. See ISSUES.md → B2.

Phase 1b — Refine mapping: minimise max utility density ✓

SPS balances load, not value. If several high-utility tasks land on one core, timing blocks their optional segments even when energy is plentiful. Phase 1b rebalances utility density (paper §V.A):

ud(i) = u_i · (cum[i][N_seg] − cum[i][0]) / p_i     UD(x) = Σ ud(i) over all jobs mapped to processor x

A candidate swap is accepted only when all three conditions hold — this is the part that is easy to miss:

  1. UD imbalance strictly decreases (pair-level for 2a; max-UD level for 2b).
  2. Mandatory-utilisation imbalance between the two processors does not worsen. SPS already produced a load-balanced mapping; a swap that disturbs it leaves less timing slack on the heavier core and hurts Phase 5 even when DBF still technically passes.
  3. Mandatory-only DBF at f_max stays feasible for both affected processors.
VariantSelection strategy
2aLinear doublet scan. Enumerate all job pairs sorted by ascending |ud_a − ud_b| and swap whenever the three conditions hold. One sweep over the list.
2bOne-swap-one-scan. Repeatedly identify the processor pair with the largest UD difference, find the first pair whose higher-UD job sits on the heavier processor, swap it, then re-scan from scratch. Mirrors the SPS style.

(mapping/refine_mapping.py) — measured: UD spread 1.45 → 0.12 on testcase.py.

Phase 1b′ — Budget-aware refine v6 only

Phase 1b always balances utility density. Compared against optimal ILP mappings that is right only when energy is plentiful — the optimum concentrates when energy binds:

ρSPS UD-spreadOPT UD-spreadwhat the optimum does
0.40.5040.730concentrates (3/4 instances)
0.70.4720.511neutral
1.00.4720.295balances

With energy plentiful everything runs at fmax and the binding resource is per-processor time, so spreading optional work stops any core saturating. With energy tight, utility per energy is u_i/g(f), so the budget should go to high-u_i work while low-value work runs slowly — and running slowly costs time on its own processor. Scattering low-value jobs makes every core pay that slowdown, including the cores hosting the valuable optional work; segregating them onto donor cores localises the penalty where nothing is lost. So Phase 1b′ flips its objective on a parameter-free regime test:

energy-bound? (E_mand_fmax > B)  →  MAXIMISE Σ UD(x)²   |   otherwise → MINIMISE Σ UD(x)²

It also judges DBF and load balance at the operating frequency f̂ = max{f : E(W_mand, f) ≤ B} rather than at fmax, because a tight budget inflates effective times by 1/f̂. (mapping/budget_refine.py)

Phase 1c — Mapping-level local search v6 only

Best-improvement search over single-job reassignments. Unlike every earlier stage, each candidate mapping is scored by running the entire downstream pipeline and reading the utility it actually achieves — the real objective, not a proxy.

for each round (MAP_LS_ROUNDS = 2):
    for each job, for each other processor (capped at MAP_LS_MAX_MOVES = 24):
        trial   = mapping with that ONE job moved
        u, feas = full_pipeline(trial)        # phases 4 -> 5 -> 6 -> 6b
        remember the best strictly-improving trial
    apply it; stop when no move improves

Infeasible candidates are discarded and the incumbent is replaced only on strict improvement, so the result is never worse than the mapping handed in.

It also guards Phase 1b′. Because 1b′ optimises a proxy, it can land on a mapping the pipeline scores lower than plain SPS. Both are scored on the real objective and the better is kept before 1c starts — a guard added after a first run regressed one instance (91.17 vs 108.89). With it, v6 beats v5b on 34 instances, ties on 16, and loses on 0.

The cost: Phase 1c is ~156× Phase 1

Measured on the ρ=0.7 instances (J = 10–13 jobs, 2 processors):

The search is not what costs. Phase 1c examines only J × (P−1) single-job moves per round — fewer candidates than Phase 1b′ considers. The expense is entirely the scoring function: it is ~5× dearer than all of Phase 1, and it is called ~25 times instead of once.

30.91 ms  =  ~25 evaluations × 1.11 ms  =  28.7× one pipeline  =  156× Phase 1

Phases 1 and 1b′ are fast because they never build a schedule — they optimise surrogates that are pure arithmetic on per-processor aggregates. Phase 1c abandons the surrogate deliberately: the only way to know what a mapping is worth is to schedule it. That is also exactly why it succeeds where 1b′ alone does not.

One evaluation is itself a nest of loops with DBF at the bottom — and Phase 5 runs several times inside a single pipeline call:

Phase 1c
 └─ x25  full pipeline
     ├─ Phase 4   iterative scale-down, DBF check per attempt
     ├─ Phase 5   multi-pass greedy: per pass, per job -> min_slack_for_job
     ├─ Phase 6   O(J^2) giver/receiver pairs; every accepted swap RE-RUNS Phase 5
     └─ Phase 6b  per round: shadow prices over all jobs, then Phase 5 AGAIN
                              |
                    min_slack_for_job / check_all_timing,  each O(P . |A| . |D| . J)

Scaling — the real concern. total ~ rounds × min(J·(P−1), MAP_LS_MAX_MOVES) × pipeline(J) and pipeline(J) is superlinear in J (Phase 6 is O(J²); |A| and |D| both grow with J). At J=13 this is 31 ms and invisible — the whole 90-instance sweep runs in under 3 s. But the move count grows as J·P while each evaluation gets dearer. MAP_LS_MAX_MOVES = 24 caps the first factor, which bounds runtime but means the search covers a shrinking fraction of the neighbourhood as J grows — on a large instance it would examine 24 of potentially hundreds of moves.

If it must scale, use a cheaper screen, not a smaller search: (1) two-stage evaluation — rank candidates by the 1b′ proxy, full-evaluate only the top few; (2) restrict moves to the most-loaded / highest-UD processor; (3) warm-start each evaluation from the incumbent schedule instead of rebuilding from k=0, f_max; (4) early-abort a pipeline once its partial utility cannot beat the incumbent. None is implemented — none is needed at current instance sizes.

Phase 1M — Multi-start mapping v7

Both v7 mapping phases fall out of a single measurement of where Phase 1c's time went:

Phase 1 = 0.20 ms  ·  one pipeline = 1.11 ms  ·  Phase 1c = 30.91 ms (≈25 pipelines)

Phase 1c examines only J×(P−1) single-job moves — fewer candidates than Phase 1b already considers. So its expense is not the search, it is the scoring: every candidate mapping must be run through the whole downstream pipeline (4 → 5 → 6 → 6b) to read the utility it really achieves.

If scoring is the cost, spend it on structurally different mappings rather than on 25 small perturbations of one. Phase 1M builds seven candidates, scores each with one pipeline run, and keeps the best feasible one:

CandidateWhat it is
spsquantum SPS (criss-cross), Phase 1 as-is
sps+refine2bSPS then Phase 1b (balance utility density)
sps+budgetSPS then Phase 1b′ (budget-aware refine)
wfdWorst-Fit Decreasing — each job to the least-loaded core
ffdFirst-Fit Decreasing — first core that still fits under 1.0
bfdBest-Fit Decreasing — the core left with the least slack that fits
donordonor/harvester — deliberately concentrates utility density

Seven pipelines (≈7.8 ms) instead of twenty-five (≈31 ms), exploring seven basins rather than 25 steps inside one. Infeasible candidates are discarded; if none is feasible the first is kept, so the phase cannot return worse than SPS alone.

Three things worth noticing. (1) wfd is exactly the paper's own §V.B "Heur1.0 / Baseline" prescription — "tasks in decreasing order of utilization … map to the first least utilized processor" — so packers.py implements the paper's baseline as a side effect. (2) donor is the Phase 1b′ "concentrate" idea built directly into a mapping rather than reached by swapping: low-utility donor jobs are packed onto a dedicated subset of cores that can then run slowly without costing any optional work, while high-utility harvesters keep their timing slack on the rest. (3) wfd, ffd, bfd and donor bypass quantum_sps_mapping entirely, so they are immune to the proc_util defect (ISSUES.md → B2) — which is part of why v7 is comparatively insulated from it. (mapping/multistart.py, mapping/packers.py)

Phase 1R — Guided repair v7

After the pipeline converges on the chosen mapping, diagnose_blocked() walks every job that still has an unused optional segment and asks why it was not scheduled, attributing the blocked utility to one of two causes:

  • TIME — min_slack_for_job < add_time: that processor's DBF windows are full.
  • ENERGY — E_slack < add_energy: the global pool cannot pay for it.

The distinction is decisive, and it is the same energy-global / time-local asymmetry that drives Phase 1b′:

If a processor is TIME-blocked, moving a low-value job off it can genuinely help — time is a per-core resource, so the pressure can be relocated. If it is ENERGY-blocked, no mapping change whatsoever can help, because energy is a global budget: shuffling jobs between cores does not create energy.

So Phase 1R skips energy-blocked processors outright. That is the "guided" part — v6's Phase 1c spent most of its 25 expensive evaluations on processors where reassignment was provably useless. Each move targets the processor with the most TIME-blocked utility, sends to the one with the least, and relocates the lowest utility-density job (trying the three least valuable). Strict improvement only, capped at GUIDED_REPAIR_MOVES = 4, so it cannot regress. (mapping/multistart.py::diagnose_blocked, guided_repair)

Phase 1L — Short local search v7 · disabled

A brief single-job local search from the repaired mapping, scored on the same real objective with strict-improvement acceptance. Currently switched off: LS_ROUNDS = 0 (LS_MAX_MOVES = 10), on the grounds that the evaluation budget has already been spent by 1M and 1R. Worth knowing before looking for its effect in the output. (solvers/heuristic_v7.py, mapping/budget_refine.py::mapping_local_search)

Net result. v7 reaches 3.97% mean gap in 15.1 ms against v6's 3.52% in 28.8 ms — roughly half the cost for 0.45 points more gap — and it never loses to v5b (31 better / 19 equal / 0 worse).

Phase 2 — Left shift (diagnostic) ✓

Simulates non-preemptive EDF-order packing on each processor:

start = max(proc_avail, release)  ·  finish = start + e_eff(i,k,z)  ·  slack = deadline − finish

Ordering. Jobs are sorted by (deadline, release, job-id). The release-time tie-break is load-bearing: when two jobs share a deadline the earlier-released one is packed first, because it becomes available sooner and packing it first wastes less idle time. Previously the deadline tie was settled by list order, which made the reported slack depend on dictionary insertion order — measured at 2.0 vs 12.0 on the same instance. Since Phase 2 is a diagnostic, that bug corrupted a number people read rather than a decision the solver made.

Read this as an approximation, not a feasibility test. The real system is preemptive EDF, so left-shift only estimates where idle time sits. Hard feasibility is always decided by DBF. In v3–v5b Phase 2 is run once and its output is printed but never gates a decision — it is informational. (phases/left_shift.py)

Phase 3 — Energy slack ✓

Reports Δe = B − E_consumed at the current (all-f_max, mandatory-only) state. This is the number printed as E_slack, and it may legitimately be negative — on its own it is not a verdict.

The terminal test is separate, and is deliberately not taken at f_max. Infeasibility is declared only when B < min_possible_energy(), a floor that places every job at its cheapest available frequency and ignores timing entirely:

E_floor = Σi,j minf ∈ F E(cum[i][kij], f)

Two things follow. First, testing the budget at f_max would be wrong: Phase 4 exists precisely to lower frequency, and with α=0.15, β=1.0 the cost per unit of work falls from 1.15 at f_max to 0.533 at f*≈0.42. An instance can therefore bust its budget at f_max and still be comfortably schedulable; the old test declared exactly those instances infeasible. Second, ignoring timing only makes the bound looser, so B < E_floor is a genuine necessary condition for infeasibility — if it holds, no frequency assignment whatsoever fits the budget, and stopping is safe. (phases/energy_slack.py::min_possible_energy)

Phase 4 — Aggressive frequency scaling ✓

Lowers frequencies only as far as needed to reach energy feasibility — it is not an energy minimiser. If the schedule already fits the budget at its current assignment, Phase 4 returns immediately having changed nothing.

Candidate order: energy saved per unit of time cost, descending. Each pass ranks every available downshift by

score = ΔEsaved ÷ ΔTcost

and applies them best-first. This replaced plain task-index order, and the reason is that DBF slack is the resource Phase 5 needs most: index order can burn timing slack on poor trades and then fail to reach the budget at all on instances that are in fact schedulable. Ranking by the exchange rate spends the least slack per unit of energy recovered. Each step still:

  • skips any candidate yielding no energy saving (E_new ≥ E_cur) — below f*, slowing down costs both energy and time;
  • reverts the step if the full DBF check fails;
  • stops the instant E_total ≤ B.

Why the gate stays, and what now covers its blind spot. Ungated, Phase 4 drove 98 jobs toward f*, saturated the DBF windows with inflated mandatory work and starved Phase 5 of time (utility fell to ~4) — hence the "do nothing if already feasible" gate. But that gate has the opposite failure mode under a tight budget: it under-scales and starves Phase 5 of energy. Measured at ρ=0.7 on an 8-task instance, mandatory-at-f_max = 92.00 against B = 96.60, so Phase 4 returned immediately and left only 4.60 energy for optional work — where slowing down would have freed roughly 48. Neither "always scale" nor "scale only when over budget" is correct; the decision needs marginal utility-per-energy. That is now Phase 6b's job, which makes the trade globally with shadow prices rather than patching Phase 4's rule. (phases/aggressive.py)

Phase 5 — Greedy optional segments ✓

The main utility engine. Jobs are visited in a stable order sorted by (−u_i, task_id, job_id); each outer pass adds at most one segment per job, and the outer loop repeats until no addition succeeds. For a candidate job j* three cases are tried in order:

CaseConditionAction
(i) add outright min_slack ≥ add_time and E_slack ≥ add_energy commit the segment. No other job is disturbed.
(ii.A) raise j*'s freq timing blocks, but energy is available step j* up one frequency level (shrinking its execution time) so the segment fits; re-verified with a full check_all_timing.
(ii.B) global energy donation timing is fine but energy blocks: min_slack ≥ add_time and E_slack < add_energy rank every job in the system by time paid per unit energy freed and step donors down one level, several if needed, until the shortfall is covered. Then add the segment, re-verified with a full check_all_timing.

What changed in ii.B, and why. It previously took a single donor, restricted to j*'s own processor and to jobs with u_i ≤ u_{j*}. Both restrictions were removed:

  • Same-processor was an artificial limit. Energy is a global budget, so a donor anywhere can fund the segment. (Donors on j*'s own processor in fact make its timing worse — the final DBF check catches that.)
  • The u_i rule guarded a cost that does not exist. Frequency does not appear in the utility function (paper Eq. 8), so lowering a donor's frequency costs it zero utility. It costs only time, on its own processor — which is checked directly. Donors are therefore ranked purely by how cheaply they yield energy.
  • ii.B is now attempted only when energy is the blocker. Donating energy cannot fix a timing shortfall, so trying it in that case was wasted work.

Note on ii.A. The module docstring still describes raising frequency as saving "exec time and energy in the default model" — that wording predates the current constants. With α=0.15, β=1.0 the energy-optimal frequency is f*≈0.42, so stepping up from anywhere above f* always costs energy. The guard computes the real ΔE and so stays correct, but the case is close to dead in practice: instrumented over 13 runs, ii.A fired once while ii.B fired 25–47 times per run.

The timing gate is min_slack_for_job — the minimum DBF window slack over every window containing the job — which is sufficient without a full DBF recomputation in case (i). (phases/greedy.py)

Phase 6 — Best-first pairwise segment swap ✓

Escapes the local optimum Phase 5 leaves behind. Each round:

  1. Search every (giver, receiver) pair — giver = any job with ≥1 active optional segment, receiver = any job with < N_seg. With the giver's last segment tentatively removed, require: net = u_recv · e_recv_next − u_give · e_give_last > 0 plus the energy balance E_freed − E_cost ≤ E_slack and the receiver's timing min_slack ≥ add_time.
  2. Execute the single swap with the highest net gain, then re-verify with full check_all_timing.
  3. Fill pass — re-run Phase 5 to capitalise on whatever the swap freed.
  4. Repeat until no improving swap exists.

Swaps may cross processors: energy is a global budget, so dropping a low-value segment on P0 can fund a high-value one on P1. (phases/swap.py)

Phase 6b — Frequency ↔ segment trade ✓

The structural gap Phases 4–6 leave open: none of them ever asks whether the energy freed by slowing a job down is worth more than the time it costs. Phase 4 stops at feasibility; Phase 5 spends whatever happens to be left over. Measured, that left the heuristic 40–58% below the exact optimum once energy binds.

Phase 6b prices both scarce resources off the current solution. For work w on task i running at frequency f, with g(f) = α/f + βf²:

utility per ENERGY = u_i ÷ g(f)   ·   utility per TIME = u_i · f

Both are conveniently independent of w. Two shadow prices are then read off the current state — no tuned constants anywhere:

  • λ = max u_i/g(f) over segments blocked only by energy — "what one more unit of energy would buy";
  • μ = max u_i·f over segments blocked only by time — "what one more unit of time would buy".

Because frequency does not appear in the utility function, lowering a job one level costs zero utility directly — it only frees ΔE and consumes ΔT. So the move is worth making exactly when

λ · ΔE  >  μ · ΔT

Safety. Candidates require ΔE > 0, so f* is never crossed (below it a downshift costs both energy and time). Every move is DBF-verified — donor window slack first, then a full check_all_timing before it is kept. Acceptance is strict-improvement with best-so-far restore, so the phase can never return a worse schedule than it was handed; the worst case is a no-op. Deterministic, with fixed tie-breaking and no randomness. (phases/freq_trade.py)

Phase 7 — Double-giver swap claudeoptimal only

Some receivers are too expensive for any single-giver swap to unlock. Phase 7 removes the last optional segment of two givers simultaneously to open enough combined timing + energy room for one receiver. The giver pool is every job with ≥1 active segment, sorted by ascending marginal utility (cheapest segments destroyed first) and truncated to _MAX_DG_CANDIDATES = 20 — without that cap the pair enumeration is O(n³). (solvers/heuristic_claudeoptimal.py::_phase_double_giver_swap)

Phase 8 — Iterated greedy (destroy / reconstruct) claudeoptimal only

A metaheuristic layer that escapes optima no local move can. Each of _IG_ITERATIONS = 8 rounds:

  1. Score every active optional segment by utility per unit execution time: density = u_i · (cum[k] − cum[k−1])  /  add_time,   add_time = (cum[k] − cum[k−1]) / f_z
  2. Destroy the lowest-density _IG_DESTROY_FRAC = 33% — the segments that occupy the most schedule for the least value, freeing timing density for better ones.
  3. Reconstruct with Phase 5 (greedy) followed by Phase 6 (pairwise swap).
  4. Accept only if total utility strictly improves; otherwise restore the incumbent best.

The best solution found is always restored in-place at the end, so Phase 8 can never make the result worse than the Phase 6 output. (solvers/heuristic_claudeoptimal.py::_phase_iterated_greedy)

Not implemented: paper §V.B "Heur1.0 / Baseline"

The paper also defines a separate, simpler 2-phase baseline that is absent from the codebase — there is no probabilistic acceptance, annealing, or worst-fit mapping anywhere in usrt/. It is a distinct algorithm, not one of the versions below:

  • Phase 1 — mapping. Tasks in decreasing utilisation order; assign each to the least-utilised processor; feasibility by a plain utilisation check (the paper notes DBF is not needed yet). Effectively Worst-Fit Decreasing.
  • Phase 2 — local search over eight operations: inc/dec frequency, inc/dec optional segment, and the four combinations. Each iteration takes the best improving move, and probabilistically accepts a worsening one, with the acceptance probability decaying geometrically — simulated annealing in all but name.

Two of its operations lie outside our design space: O7 (dec freq + inc optional segment) and the segment-decreasing moves. O7 is precisely the trade our heuristics cannot make, and it is the one that cost them 30–47% under tight budgets (§8). It is therefore possible that the paper's own baseline outperforms v5b in the energy-bound regime — worth measuring before publishing any "we beat the baseline" claim.

6. The Online Phase

At runtime jobs finish early (ACET < WCET), freeing time slack Δt (processor-local, perishable) and energy slack Δe (global, accumulative). A precomputed DP decides, per completion, how to spread that slack over downstream jobs to add optional-segment utility — paper §VI + the online design doc.

The DP

V[j][Δt][Δe] = max(at,ae) { gain(j,at,ae) + V[j+1][Δt−at][Δe−ae] }
  • Exact breakpoint representation — each level is the Pareto frontier of reachable (req_t, req_e, value) points, not a dense grid (no quantisation until capped). value_function.py
  • Per-processor DP + shared global energy — one ProcessorDP per core (time is local); a single SharedEnergyPool guarded by a semaphore couples them. dp.py, energy_pool.py
  • Builds from offline k_off — online adds segments beyond the offline count (design doc Issue 2). actions.py
  • Utility-density arbitration for the shared pool on contention (paper §VIII / Approach C). density.py
  • Dynamic-DBF commit guarantee — every applied move re-checked against the exact per-processor DBF + energy pool; never a deadline miss or budget overrun. controller.py

8. The α/β (DVFS) Regime Finding

Energy per unit work g(f)=α/f+βf² is convex with minimum at f* = (α/2β)1/3 — depends only on the ratio r=α/β. Which frequency is energy-optimal (and whether frequency is even a decision) falls into three regimes:

RegimeConditionOptimal fFrequency a real decision?
Leakage-dominatedα ≥ 2β  (r ≥ 2)f_max No — f_max wins on time and energy (degenerate)
Balanced / interior2β·f_min³ < α < 2βf* (interior) Yes — trade-off along [f*, f_max]
Dynamic-dominatedα ≤ 2β·f_min³f_min Yes — whole [f_min, f_max] efficient

For the testcase set (f_min=0.3): r ≥ 2 → f_max; 0.054 < r < 2 → interior; r ≤ 0.054 → f_min. Old constants α=1,β=0.5 → r=2 (exactly degenerate); current α=0.15,β=1.0 → r=0.15 (interior, DVFS live).

Consequence: frequency only matters when (a) the ratio is in the interior band and (b) the energy budget is tight enough that f_max-everywhere is infeasible. The current B=400 is energy-loose, so time (not energy) binds — which is why DVFS gains look small even with live constants.
