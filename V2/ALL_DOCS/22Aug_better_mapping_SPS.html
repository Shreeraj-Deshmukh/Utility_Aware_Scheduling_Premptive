Better SPS Mapping — 22 August

⚠ BEHIND THE CODEBASE · re-verified against the code 4 Sep 2026

The code described here is current — v7, Phase 1M, Phase 1R, the packer candidates and LS_ROUNDS = 0 all match the tree. The problem is with one conclusion.

Caveat on every SPS-mapping number. mapping/quantum.py accumulates proc_util across the whole hyper-period instead of releasing it, so once it passes 1.0 every later quantum reports MAND_OVERUTIL and its jobs fall through to a min-util round-robin — 22 of 30 jobs on testcase.py, 3%–42% on generated instances. This is finding B2 in usrt_code_review_report.html (12 Jun), still unfixed. Any SPS-vs-alternative comparison is therefore measuring a partly-broken SPS.

Re-running the multi-start with that accumulation neutralised flips the winner: sps 222.24→239.80, sps+refine2b 227.33→242.88, wfd unchanged at 234.54 (it never touches SPS). v7’s final goes 236.04→242.88. So §2’s “plain WFD beat every SPS variant” does not survive the fix on this instance. That is not a claim the fix is an improvement — across 12 generated instances the same probe swung −14% to +11%, mean −2%. The honest statement is that SPS-vs-alternative comparisons are unsafe until re-measured on dry_run_tc.

The gap decomposition showed the mapping, not the frequency/segment search, is the dominant error at tight budgets. Phase 1c (v6) attacks it but costs ~25 full pipelines. This is an attempt to buy the same quality far more cheaply, measured on the identical 90 test cases.

2 · What v7 does

BEHIND THE CODEBASE · 4 Sep 2026The multi-start mechanism below is accurate. The scores it reports for the sps, sps+refine2b and sps+budget candidates are not — all three run through the partly-broken quantum_sps_mapping. wfd, ffd, bfd and donor bypass SPS and are unaffected.

The reframe that drove the design: Phase 1c's expense is the SCORING, not the search. It examines only J×(P−1) single-job moves — fewer candidates than Phase 1b considers — but scores each by running the entire downstream pipeline (1.11 ms), ~25 times. So the lever is not "search less"; it is "spend those evaluations on better candidates".

Phase 1M — multi-start

Build several structurally different mappings and score each with exactly one pipeline:

CandidateWhat it is
spsQuantum SPS, as today
sps+refine2bSPS + Refine Mapping 2b (v5b's mapping)
sps+budgetSPS + budget-aware refine (v6's Phase 1b′)
wfdWorst-Fit Decreasing — also exactly the mapping the paper's §V.B "Heur1.0/Baseline" prescribes
ffd / bfdFirst-Fit / Best-Fit Decreasing
donordeliberately CONCENTRATES utility density — low-value jobs segregated onto donor cores that can run slowly without costing optional work

Five structurally different mappings explore far more than twenty-five single-job moves away from one basin. Every candidate is DBF-verified before scoring, so an infeasible mapping can never be returned.

The multi-start justified itself immediately. On testcase.py: sps 222.24, sps+refine2b 227.33, sps+budget 227.51, wfd 234.54, ffd/bfd 178.80, donor 207.23. Plain WFD beat every SPS variant — the basin SPS lands in is not always the best one, and no amount of local search from SPS would have found it.

Phase 1R — guided repair

Rather than trying all J×(P−1) moves blindly, diagnose why a processor still has unscheduled optional utility:

for each processor, classify each blocked segment:
    min_slack < add_time   -> TIME-blocked
    E_slack   < add_energy -> ENERGY-blocked

target  = processor with the most TIME-blocked utility
move    = its LOWEST utility-density job -> the least congested processor
skip    = ENERGY-blocked processors entirely
The skip is the point. Energy is a global budget, so no reassignment can create any — a processor blocked on energy cannot be helped by moving jobs around. Blind local search spends most of its evaluations on exactly those processors.

3 · A negative result worth recording

Adding a short local search on top of the multi-start winner did not pay. A 10-move, 1-round search raised the cost from 14.0 ms to 27.9 ms — erasing the entire speed advantage — while the gap stayed worse than v6 (5.10% vs 4.77%). Starting from the best of seven structurally different mappings, extra single-job moves buy almost nothing: the diversity has already been spent. It is disabled in the code (LS_ROUNDS = 0) with the measurement recorded alongside it.

This is the same lesson as the LP experiment: a better-informed starting mapping helps, but grinding local moves around any single mapping has sharply diminishing returns.

A bug this exposed

Setting LS_ROUNDS = 0 made every v7 run crash — 84 error rows. The cause was a latent defect in mapping_local_search (written for v6): it returns dict(rounds=rnd + 1, ...) referencing the loop variable, which is undefined when the loop body never executes. Dormant while max_rounds was always ≥ 1. Fixed.

7 · Verdict

  1. Multi-start is the right idea; it is not a free win. v7 gets within 3.97% at 15.1 ms versus v6's 3.52% at 28.8 ms. If runtime matters — and it is the entire argument for a heuristic over an ILP — v7 is the better engineering choice. If only quality matters, v6 still edges it.
  2. v7 dominates v5b outright (31 better, 19 equal, 0 worse) at under 10× v6's cost, so it is a strictly better default than the current v5b.
  3. WFD earns its place twice — it won the multi-start on testcase.py, and it is the mapping the paper's unimplemented §V.B baseline requires. That gap is now closed as a side effect.
  4. Diminishing returns are real. Local search on top of multi-start did not pay; neither did LP-rounded mappings earlier. Both point the same way: the mapping sub-problem is genuinely hard, and the remaining gap will not fall to more search around one incumbent.
  5. Still to try: sizing the donor/harvester split from the measured energy deficit rather than defaulting to one core; and incremental evaluation (a single-job move perturbs exactly two processors, yet the whole pipeline is re-run), which would cut the cost of every mapping stage at once.
