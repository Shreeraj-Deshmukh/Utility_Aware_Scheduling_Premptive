1. Why the Code Looks "Strange": It Stores Requirements, Not a Table

The design doc draws the value function as a dense grid you index by slack: V[j][Δt][Δe] = value. The natural expectation is a 2-D array. The code never builds that array. That is the one decision behind almost everything that looks unfamiliar.

The inversion. For a fixed job j, the table V[j][Δt][Δe] is a step function: non-decreasing in both Δt and Δe, flat except at a handful of jumps. Instead of storing the value at every (Δt, Δe), the code stores only the jump points — and it stores them inverted: for each achievable value, the minimum slack required to reach it. That pair of minimums is (req_t, req_e). One such jump point is an Entry.

Doc's mental model (dense)The code's model (sparse, inverted)
V[j] = 2-D array indexed by (Δt, Δe).
Lookup = V[j][dt][de].		 V_levels[j] = list[Entry], each Entry = one jump:
"you need ≥ req_t and ≥ req_e to get value."
Lookup = query(): best value whose req fits.

Why do it this way? Three reasons, all visible in the code:

  • Float costs. Real execution times/energies are floats (e_m = 2.451382…). A dense table would force you to quantise the axes and eat rounding error. The breakpoint set is exact at any float (doc Issue 5 / §7.2 "aggregate states" — here it falls out for free).
  • Sparsity. A chain of jobs with a few segments each has only a few reachable cost vectors. The frontier is tiny; a dense grid would be mostly duplicated flats.
  • Reconstruction. Each Entry carries a back-pointer nxt to the downstream entry it was built from, so the optimal per-job plan is recovered by following pointers — no second pass over a table.
If you remember one thing: an Entry's (req_t, req_e) is "how much slack this costs," and value is "how much utility you get." query(dt, de) = "of all entries I can afford, give me the most valuable." That is the whole engine.

2. A Real Trace Through compose() and query()

This is the design document's Example 1 (3 jobs, single processor), run through the actual functions. It shows how the Pareto entries are the table.

Inputs — the action lists (from worked_examples.py)

# Action(a_t, a_e, gain, k, z)   — energy == time in the doc's simplification
J1 = [Action(0,0,0.0,0,0), Action(2,2,6.0,1,0), Action(3,3,9.0,2,0)]
J2 = [Action(0,0,0.0,0,0), Action(3,3,3.0,1,0)]
J3 = [Action(0,0,0.0,0,0), Action(1,1,2.0,1,0), Action(4,4,8.0,2,0)]

Step A — build the last level V[3] = compose(J3, base_level())

base_level() is a single Entry(req_t=0, req_e=0, value=0, nxt=None). compose takes the Cartesian product (each action × each downstream entry), adds costs and values, clamps negatives to 0, then prune()s to the Pareto frontier:

# action × the one base entry → candidate Entry(req_t, req_e, value, k, nxt=0)
(0,0,0.0,k0) → Entry(req_t=0, req_e=0, value=0, k=0)
(1,1,2.0,k1) → Entry(req_t=1, req_e=1, value=2, k=1)
(4,4,8.0,k2) → Entry(req_t=4, req_e=4, value=8, k=2)
# none dominates another (more slack buys more value) → all 3 kept
V_levels[2] = [ (0,0,v0), (1,1,v2), (4,4,v8) ]   # this list IS the V[3] table

Now query() reconstructs any table cell on demand:

query(V[3], dt, de)entries affordable (req_t≤dt, req_e≤de)best valuedoc cell
dt=3, de=3(0,0,0), (1,1,2)2V3[3][3]=2 ✓
dt=4, de=4(0,0,0), (1,1,2), (4,4,8)8V3[4][4]=8 ✓

Step B — build V[2] = compose(J2, V[3]) (this is where lookahead appears)

Each J2 action is paired with each downstream entry of V[3]. The downstream entry's req is added to the action's cost; its value is added to the gain; nxt records which downstream entry was used:

action (0,0,0.0) "skip J2"  × V3(0,0,0) → Entry(0,0, 0)   nxt→V3(0,0,0)
                            × V3(1,1,2) → Entry(1,1, 2)   nxt→V3(1,1,2)
                            × V3(4,4,8) → Entry(4,4, 8)   nxt→V3(4,4,8)
action (3,3,3.0) "do  J2"  × V3(0,0,0) → Entry(3,3, 3)   nxt→V3(0,0,0)
                            × V3(1,1,2) → Entry(4,4, 5)   nxt→V3(1,1,2)
                            × V3(4,4,8) → Entry(7,7,11)   nxt→V3(4,4,8)
# prune: (4,4,5) is dominated by (4,4,8) — same req, less value — DROPPED
V_levels[1] = [ (0,0,0), (1,1,2), (3,3,3), (4,4,8), (7,7,11) ]
The non-greedy decision, made by pruning. At query(V[2], 4, 4) the affordable entries are (0,0,0),(1,1,2),(3,3,3),(4,4,8) → best is 8, which is the (4,4,8) entry whose nxt points to J3's big segment. That entry came from the "skip J2" action. So the code decides "skip J2, give all slack to J3" purely because the dominated (4,4,5) "do J2" candidate was pruned — exactly the doc's V2[4][4]=8 result, reached with no special-case logic.

3. Every Datatype, With Its Fields

The whole subsystem is built from one class with a back-pointer plus five namedtuples and two owner classes. Knowing these makes every function readable.

TypeDefined inKindFieldsRole

4. value_function.py — the DP Engine (model-agnostic)

This module knows nothing about tasks, processors, or energy models. It only manipulates Entry lists and Action tuples. That is deliberate — it's why the same code reproduces the doc's integer tables and drives the float-cost real schedule.

FunctionSignatureWhat it does / value flow
base_level()() → [Entry] Terminal level V[N]: one Entry(0,0,0, k=None, nxt=None). Seeds the right-to-left recurrence and guarantees a "do-nothing" fallback so query never returns None.
compose()(actions, downstream) → [Entry] The recurrence. For every (a_t,a_e,gain,k,z) × every downstream Entry d: req_t = max(0, a_t + d.req_t), req_e = max(0, a_e + d.req_e), value = gain + d.value, nxt = index(d). Then prune. Output indexes into downstream.
prune()(entries) → [Entry] Pareto filter. Sort by (req_t↑, req_e↑, value↓); keep an entry only if no kept entry already needs ≤ both resources for ≥ value; drop kept entries the new one dominates. O(n²), fine for tiny frontiers.
query()(level, dt, de) → Entry The online lookup. Among entries with req_t ≤ dt and req_e ≤ de, return max value; ties broken toward the smaller req_t+req_e (leave more slack for later).

The clamp max(0, a_t + d.req_t) — the part that looks wrong but isn't

When a job runs faster than baseline (Option 4), its a_t is negative — it returns time to the pool. Adding it to the downstream requirement lowers what the upstream must supply. The clamp at 0 says: a job cannot create usable surplus beyond what the downstream actually needs, because d.req_t is already the minimal requirement for that value level. Without the clamp you would record a negative requirement and over-credit the chain. This is precisely how the conversion options enter the table (module docstring spells it out).

5. actions.py — the 4-Option Action Set

One function, build_job_actions(), turns a job's offline decision into the list of online moves the DP may pick. This is the only place the energy model (energy_val, e_eff_val from usrt/models.py) is touched per job.

def build_job_actions(i, k_off, z_off, cum, N_seg_i, freq_set, u_i, time_cap):
    base_eff = e_eff_val(cum[i][k_off], freq_set[z_off])   # offline effective time
    base_en  = energy_val(cum[i][k_off], freq_set[z_off])  # offline energy
    for k in range(k_off, N_seg_i+1):        # only ADD segments (A1)
        gain = u_i * (cum[i][k] - cum[i][k_off])     # utility at f_max work
        for z in range(len(freq_set)):           # any target frequency
            a_t = e_eff_val(cum[i][k], fz) - base_eff
            if a_t > time_cap: continue          # timing gate (A2)
            a_e = energy_val(cum[i][k], fz) - base_en
            actions.append(Action(a_t, a_e, gain, k, z))
  • Baseline-relative. Every a_t, a_e is measured against the offline (k_off, z_off), so the (k_off, z_off) action is always present as Action(0, 0, 0, …) — the paper's Option 1 (save).
  • gain depends only on k. Utility is earned on fmax-normalised work (paper Eq. 8), so several (k, z) share a gain; pruning later keeps only the energy/time-efficient ones.
  • Timing gate only. Energy is not filtered here — it's a global, replenishable pool handled by req_e in the DP and by the controller. Only the local time cap is applied at action-build time.
  • Result is sorted with the baseline action first, for stable, readable reconstruction.

6. dp.py — Per-Processor Precompute & Reconstruction

Wraps the engine for one processor and adds the back-pointer walk.

build_processor_dp(x, …) → ProcessorDP

  1. _edf_order() sorts the processor's jobs by (deadline, release, i, j) into jobs_x.
  2. Builds a JobSlot per job: position, offline (k_off, z_off), and a time_cap. The cap is time_caps[(i,j)] if the caller passed one (the controller does), else min_slack_for_job(...) from usrt/dbf/slack.py.
  3. Right-to-left loop: V_levels[N]=base_level(), then for s = N-1 … 0: V_levels[s] = compose(build_job_actions(slot s), V_levels[s+1]).
Why "precompute once" works. V_levels[s] is the value function over every suffix jobs[s:]. So when the job at position c completes early, the downstream chain is jobs[c+1:] and the answer is already sitting in V_levels[c+1] — the online step is a lookup, not a rebuild.

ProcessorDP.distribute(start_pos, dt, de) → (total_value, [PlannedAction])

This is the reconstruction — it turns the chosen Entry into concrete per-job decisions by following nxt:

e = query(V_levels[start_pos], dt, de)        # best affordable entry
total = e.value
while e.nxt is not None:                   # walk the back-pointer chain
    if e.k != slot.k_off or e.z != slot.z_off:  # job actually changed?
        decisions.append(PlannedAction(... k=e.k, z=e.z, a_t=e.a_t, a_e=e.a_e ...))
    e = V_levels[s+1][e.nxt]                   # hop to the downstream entry it used
    s += 1

Only jobs whose (k, z) differs from their offline baseline are emitted (a job that the DP decided to leave alone produces nothing). best_value() is the same lookup without reconstruction, used by the validator.

Code smell flagged honestly: after the while loop there is a trailing "last consumed level" block. Given base_level's entry has k=None and every composed entry carries an integer nxt, that block is effectively defensive/unreachable in the current construction — see §12.

7. density.py — Global Energy Arbitration

Time is processor-local (separate DPs). Energy is one shared pool, so when several processors could spend it, the code resolves contention with the paper's "higher future density wins" rule.

FunctionReturnsLogic
future_utility_density(x, t, …)float ρ_x(t) Σ over jobs on x released at/after t of u_i · (cum[i][N_seg_i] − cum[i][seg_k]) / p_i — i.e. still-addable optional utility per period, using the current committed seg_k.
arbitrate_energy(pool, densities, mode){x: energy_cap} proportional (default): cap_x = pool · ρ_x / Σρ. strict: the single highest-ρ processor gets the whole pool. If all ρ≈0, split equally.
Advisory, not a hard cap. The returned cap only limits what distribute() is allowed to plan on this processor. The hard guarantee (never exceed B) is enforced separately by the controller against the whole pool.

8. controller.py — the Runtime Owner

The only stateful, model-aware object. It holds the live schedule (seg_k, freq_idx, mapping), one ProcessorDP per processor, the energy_pool, and eff_override (actual effective times of jobs that already completed early).

Construction

  • Copies the offline schedule into mutable dicts; builds proc_jobs.
  • energy_pool = B − total_energy() — the starting slack.
  • Builds dps[x] for each processor via _build_dp(x), which passes a time_caps of deadline-interval (d − r) per job (not min_slack_for_job).
  • pos_of[(i,j)] records each job's EDF position.
The time_caps override — the single most important runtime subtlety. At build time the static min_slack_for_job is ~0 (the offline greedy already consumed all static slack), which would make the DP propose nothing. The controller deliberately replaces it with the loose deadline-interval cap and relies on the dynamic DBF at commit time as the real limiter. This is the change that turns a 0-utility online phase into a real gain.

on_completion(i, j, observed_dt, observed_de) — the event handler (5 steps)

x = proc of (i,j); c = pos_of[(i,j)] 1. RECORD eff_override[(i,j)] = max(0, committed_eff - observed_dt) # job ran short energy_pool += observed_de # energy returned 2. ARBITRATE densities = ρ_x(release_time) for all x caps = arbitrate_energy(energy_pool, densities, mode) de_budget = min(energy_pool, caps[x]) # this proc's share 3. LOOK UP _, planned = dps[x].distribute(c+1, observed_dt, de_budget) # downstream plan 4. GUARANTEE committed = _commit_with_guarantee(planned) # dyn-DBF + pool, trim 5. SETTLE energy_pool -= Σ committed.a_e # pay for what stuck dps[x] = _build_dp(x); refresh pos_of # lazy rebuild return Σ committed.gain, committed

_timing_ok_dynamic() — the feasibility authority

A full preemptive-EDF DBF across all processors and all (t1∈arrivals, t2∈deadlines) windows, but it sums _eff(i,j) — the actual effective time for already-completed jobs (from eff_override) and the committed WCET effective time otherwise. Because a completed job contributes less, adding work to a downstream job inside its window keeps the window demand at or below its original, already-feasible value. This is what makes the additions provably safe.

_commit_with_guarantee(planned) — trim-to-feasible

  1. Fast path: apply all planned decisions, check _timing_ok_dynamic() and energy_pool − spent ≥ 0. If both hold, keep the whole set.
  2. Else revert and re-apply greedily, highest gain first, re-verifying after each; keep a decision only if it preserves feasibility, else roll just it back.

The committed schedule therefore always satisfies the dynamic DBF and the budget — nothing probabilistic, every commit is provably legal.

9. simulator.py & worked_examples.py

OnlineSimulator — drives a whole hyper-period

  • _windfall(i, j, ratio): a job whose effective time is eff actually runs ratio·eff, freeing dt=(1−ratio)·eff and de=(1−ratio)·E(committed) (doc §1.1 model). ratio is fixed (acet_ratio) or drawn in [ratio_min, ratio_max] with a seeded RNG.
  • _event_order(): jobs in release order (≈ wall-clock), each fed to on_completion.
  • run() prints the per-event table and a summary, returning a dict with offline_utility, online_added, final_utility, wcet_energy, actual_energy, feasible. Note: C3 (energy ≤ B) binds on actual_energy = B − energy_pool, the realised consumption — not the conservative WCET commitment.
  • verify_single(i, j, dt, de): computes the DP value, runs the real event, and asserts added == dp_value (the doc's "verified trace" property).

worked_examples — pins the engine to the paper

build_levels() feeds the doc's literal Action lists to compose; table() materialises a dense grid from the step function by calling query at every integer cell; _cmp asserts it equals the published table; reconstruct() follows nxt to print the chosen actions. Both 3-job and 4-job examples (all 7 tables, traces 19.0 / 17.0 / 10.0) reproduce exactly. Run standalone: python -m usrt.online.worked_examples.

online_demo (in usrt/solvers/) — the run.py online entry

Builds the offline schedule with the v5b pipeline (Quantum SPS → Refine 2b → aggressive → greedy → swap) to get (seg_k, freq_idx, mapping), runs verify_worked_examples(), then constructs an OnlineSimulator and calls run(). One command proves both "engine matches the doc" and "online improves a real schedule while staying feasible."

10. End-to-End Value Flow (One Early Completion)

testcase.py │ load_testcase ▼ offline_schedule() seg_k, freq_idx, mapping (the precompute INPUT) │ ▼ OnlineController.__init__ │ energy_pool = B − total_energy() │ for x: dps[x] = build_processor_dp(x, time_caps = deadline-interval) │ └─ _edf_order → JobSlots → right-to-left compose() → V_levels[] ▼ ── runtime: job (i,j) finishes at ratio·eff ─────────────────────────────────────────── simulator._windfall → (observed_dt, observed_de) │ ▼ controller.on_completion(i, j, observed_dt, observed_de) │ ① eff_override[(i,j)] ← actual; energy_pool += observed_de │ ② de_budget ← arbitrate_energy(pool, ρ) [density.py] │ ③ planned ← dps[x].distribute(c+1, observed_dt, de_budget) │ └─ query(V_levels[c+1]) → Entry → follow nxt → [PlannedAction] │ ④ committed ← _commit_with_guarantee(planned) [dyn-DBF + pool, trim] │ ⑤ energy_pool −= Σ a_e; dps[x] ← rebuild ▼ (added_utility, [JobDecision]) → applied += … ; seg_k / freq_idx mutated in place

Data shape at each hop: floats (dt, de) in → an Entry chosen → a list of PlannedAction → a (possibly trimmed) list of JobDecision out, with seg_k/freq_idx/energy_pool updated as side effects.

11. The Four Paper Options ↔ Signed Deltas

There is no if option == 3 anywhere. The four options are emergent from the sign of an action's deltas, produced naturally by the nested (k, z) loop in build_job_actions:

Paper optionCode conditiona_ta_egain
1 — Savek=k_off, z=z_off000
2 — Spendk>k_off, z=z_off>0>0>0
3 — Time→Energyk=k_off, z<z_off (slower)>0<00
4 — Energy→Timek=k_off, z>z_off (faster)<0>00

The composer's max(0, a_t + d.req_t) clamp is what lets the negative deltas of Options 3/4 reduce upstream requirements. Caveat (α=1, β=0.5): energy is minimised at fmax, so Option-3/4 actions carry gain=0 and are dominated in prune — present in code, inert in practice. See §12 and dp_assumptions.html (L1).

12. Concerns & Edge Cases (code-specific)

High

E1. distribute() value can exceed what _commit_with_guarantee keeps

The DP plans against a loose per-job time_cap (deadline interval) and a scalar dt; the true preemptive-EDF coupling is only enforced at commit. When a windfall would fund several downstream jobs that share a tight window, the fast path fails and the greedy trim keeps a subset. Then the committed utility is less than distribute()'s returned total_value.

Consequence for the validator: verify_single asserts added == dp_value. That holds for single-windfall / non-conflicting chains (the worked examples), but on a contended real instance trimming can make it fail. verify_single is a single-event soundness check, not a general invariant — treat a mismatch there as "trimming happened," not "bug."
Medium

E2. Arbitration instant uses release time, and ρ filters by job_r ≥ t

on_completion arbitrates at t = job_r[(i,j)], and future_utility_density counts only jobs with release ≥ t. A high-value job already released but still pending on another processor (release < t) is excluded from that processor's ρ, so it can be under-weighted in the energy split. The split is advisory (never unsafe), but it can be sub-optimal exactly where it matters most.

Medium

E3. verify_single is not side-effect-free

It nudges energy_pool up/down and then calls the real on_completion, which mutates the live schedule and rebuilds the DP. Calling it as if it were a pure assertion will advance controller state. It's fine inside a dedicated validation run, surprising if reused mid-simulation.

Medium

E4. Energy reservation is soft across events

de_budget caps planning, but the hard commit check uses the whole energy_pool. Within one event the cap reserves energy for other processors; but the first processor to complete can still spend down the global pool before later processors get their turn (events are serialised — doc's "two early completions" question is approximated, not solved jointly).

Low

E5. Dead/defensive trailing block in distribute()

Because base_level()'s entry has k=None and every composed Entry always gets an integer nxt, the post-loop "last consumed level" block cannot append a decision the loop didn't already handle. It's harmless but misleading; worth a comment or removal to stop future readers (and you) from puzzling over it.

Low

E6. Per-job prune() is O(n²) with no hard frontier bound

Fine for the current instances (few segments × few frequencies). On a long chain with many frequencies the frontier could grow; there's no explicit cap (doc's "aggregate states" / schedule-derived bounds are not applied). Watch this if task sets or frequency levels scale up.

Low

E7. Single hyper-period; lazy full rebuild per event

The DP is built for one hyper-period's job set (no cross-period carry), and after each commit the entire affected processor's DP is rebuilt rather than incrementally patched. Correct, but it gives up the "one frozen table for the whole run" ideal — see dp_assumptions.html (L4).

Low

E8. Options 3/4 are structurally present but numerically inert

Under α=1, β=0.5 the frequency-conversion actions always carry gain=0 and lose to (0,0,0) in prune. The DVFS axis of the action set is exercised only if the energy constants are changed to put the critical frequency below fmax (no code change needed). Until then the online phase is effectively Save + Spend.
