Heuristic v5a & v5b

Utility-Density Refinement on top of Quantum SPS Mapping
v5a and v5b are identical to v4 in Phases 2–6 (energy, greedy, swap). The only addition is Phase 1b: a post-SPS remapping step that swaps individual jobs between processors to improve utility-density balance, while carefully preserving the timing and energy feasibility that SPS established. v5a uses a one-pass doublet scan; v5b uses an iterative greedy loop.

1. Motivation — Why does v4 leave utility on the table?

The Core Problem with SPS

SPS (Sum Partial Solutions) distributes jobs across processors by balancing mandatory utilisation — the fraction of each period spent on the mandatory segment. Its load metric is:

load(i) = e_m(i) / p_i

SPS guarantees that no processor is overloaded with mandatory work. But it knows nothing about optional segments. A task with a small mandatory segment but enormous optional reward potential looks identical to one with the same e_m and zero optional benefit.

The Imbalance: SPS may concentrate all the high-utility tasks (tasks with large u_i and many optional segments) on a single processor. That processor then has a huge pile of competing optional work in Phase 5. Because Phase 5 uses DBF window-slack to gate additions, a crowded processor has less slack per job, fewer optional segments get scheduled, and total utility suffers.

The v5 Fix

After SPS (Phase 1), run a refinement step (Phase 1b) that selectively swaps individual jobs between processors to spread the utility potential more evenly. This gives Phase 5 a better starting canvas where every processor has roughly equal opportunity to accumulate utility.

2. What SPS Does — and What It Misses

How SPS Works (in Brief)

Quantum SPS processes the hyperperiod in time-quanta of size gcd(all periods). At each quantum boundary, newly arriving jobs are inserted into Partial Solutions (PSs) using DPS (Determining Partial Solutions), which fills the PS with the largest gap first. The "gap" is the difference between the most-loaded and least-loaded processor in that PS, measured in utilisation units.

Gap of a PS = loads[0] - loads[-1] (in e_m/p_i units)

The result is a mapping where every processor's sum of e_m/p_i values is as close to equal as possible. This ensures EDF can schedule all mandatory segments.

What SPS Does Not See

  • The utility reward u_i earned for completing optional segments
  • How many optional segments each task has (the depth of optional work)
  • The cumulative execution time of optional segments cum[i][k]
  • Any interaction between utility rate and task frequency

Two tasks with the same e_m = 2, p_i = 10 look identical to SPS even if one has u_i = 0.01 (almost no reward) and the other has u_i = 10.0 (enormous reward per unit time).

3. Key Definitions

Mandatory Utilisation — mu(i)

mu(i) = e_m(i) / p_i

Fraction of processor time consumed by task i's mandatory segment per period. SPS balances this across processors. Tracked as proc_mutil[x].

Utility Density — ud(i)

ud(i) = u_i * (cum[i][N_seg[i]] - cum[i][0]) / p_i

Maximum utility per unit time if ALL optional segments of task i ran at f_max, every period. It combines reward rate, optional volume, and task frequency. Tracked as task_ud[i].

Breaking Down ud(i)

ComponentMeaningWhy It Matters
u_i Utility reward per job if all optionals complete Directly scales the value of scheduling this task's optionals
cum[i][N_seg[i]] - cum[i][0] Total execution time of all optional segments (e_opt_total) How much time the optionals need — affects how crowded a processor becomes
1 / p_i Jobs per unit time (frequency) Faster tasks contribute utility more often per hyperperiod

Result: ud(i) = utility earned per unit processor time in the best case. Two tasks with the same ud(i) generate the same long-run utility rate, so they are equivalent from Phase 5's perspective.

Processor Utility Density — UD(x)

UD(x) = sum of ud(i) for all jobs (i,j) mapped to processor x

Total utility potential of processor x. When UD(x) is high, x has many high-value optional segments competing for its time slots.

Processor Mandatory Utilisation — MU(x)

MU(x) = sum of mu(i) for all jobs (i,j) mapped to x

Total mandatory load on processor x. SPS keeps this balanced. The refinement must not break this balance, or Phase 5 will have less slack on some processors.

4. Doublets — The Candidate Pool

What is a Doublet?

A doublet is any pair of two jobs (from possibly different tasks) that could be swapped between processors. The full candidate pool is all C(N_jobs, 2) pairs from the entire hyperperiod.

Example: If the hyperperiod contains 12 jobs total, there are C(12,2) = 66 doublets.

How Doublets Are Sorted

Sort by ascending |ud(job_a) - ud(job_b)|

Pairs with similar utility densities come first. Why? Because swapping two jobs with very different ud values moves a lot of utility potential from one processor to the other — high risk of overshooting the balance. Pairs with similar ud values are "safe" trades that can correct small imbalances without causing large ones.

This is the same intuition as SPS's gap-first insertion: work on the smallest adjustments first to avoid oscillation. 

def _build_doublets(mapping, task_ud):
    jobs  = list(mapping.keys())              # all (i,j) pairs in hyperperiod
    pairs = list(combinations(jobs, 2))       # all C(N,2) combinations
    pairs.sort(key=lambda p: abs(task_ud[p[0][0]] - task_ud[p[1][0]]))
    # p[0] = job_a = (task_index, job_index), p[0][0] = task_index
    return pairs

Important: ud is Per-Task, Not Per-Job

All jobs of the same task i share the same ud(i) value because they all have the same u_i, cum[i][...], and p_i. So sorting by |ud(a) - ud(b)| groups together jobs from different tasks that have similar utility rates.

5. Three Swap Acceptance Conditions

A swap of job_a (on processor pa) and job_b (on processor pb) is accepted only if ALL THREE conditions hold simultaneously. Any single failure blocks the swap.

Condition 1 — Utility Density Improves

The swap must reduce the UD imbalance between the two processors.

new_UD_pa = UD(pa) - ud(job_a) + ud(job_b) new_UD_pb = UD(pb) - ud(job_b) + ud(job_a) Condition: |new_UD_pa - new_UD_pb| < |UD(pa) - UD(pb)| (strict)

In 2a this is a pair-level check. In 2b the condition is stricter: max(new_UD_P1, new_UD_pb) must be less than UD(P1).

Condition 2 — Mandatory Utilisation Balance Does Not Worsen

This is the guard added to fix the "low utility" problem that early versions of v5 had. A UD-improving swap might happen to move a high-mutil job from a lightly-loaded processor to a heavily-loaded one, destroying the timing slack that SPS carefully established.

cur_mu_diff = |MU(pa) - MU(pb)| new_mu_diff = |(MU(pa) - mu(a) + mu(b)) - (MU(pb) - mu(b) + mu(a))| Condition: new_mu_diff <= cur_mu_diff (must not worsen)
Why this matters: If MU(pa) becomes much larger than MU(pb), processor pa has less DBF slack in Phase 5. Fewer optional segments can be inserted before the demand bound is hit, directly hurting total utility — even though the UD balance looked better on paper.

Condition 3 — DBF Feasibility After Swap

Check whether the mandatory-only schedule remains timing-feasible on both affected processors as if the swap had already happened, before actually committing it.

For processor pa: temporarily remove job_a, add job_b new_pa = [jobs on pa] - {job_a} + {job_b} For processor pb: temporarily remove job_b, add job_a new_pb = [jobs on pb] - {job_b} + {job_a} DBF check: for all windows [t1, t2] on the new job list: sum of e_m(i,j) for jobs in [t1,t2] <= (t2 - t1)

The DBF (Demand Bound Function) check scans all pairs of release times and deadlines to verify that no time window is overloaded with mandatory work. This is the formal EDF schedulability condition for hard real-time tasks.

Why might DBF fail after a UD-improving swap? Two jobs from the same task on the same processor create back-to-back mandatory demands in the same timing windows. A swap that places job (i,0) and job (i,1) both on the same processor could create windows where the demand exceeds the available time.

6. Algorithm 2a — Linear Doublet Scan v5a

High-Level Idea

Make one linear pass through all doublets (sorted by ascending ud difference). For each pair, check the three conditions. Accept the swap if all pass. Never revisit a pair. Stop after one full scan.

1
Build the doublet list — all C(N_jobs,2) pairs sorted by |ud_a - ud_b| ascending.
2
For each (job_a, job_b) in order:
  • Skip if both are on the same processor (pa == pb)
  • Check Condition 1: pair-level UD improvement
  • Check Condition 2: mutil balance does not worsen
  • Check Condition 3: DBF feasibility after swap
  • If all pass: execute the swap, update UD and mutil tracking, increment counter
  • Continue to next pair (no break, no restart)
3
Finish — after the full scan, return the refined mapping. 
def refine_mapping_2a(mapping, tasks, N_prc, cum, N_seg, job_r, job_d, verbose=True):
    task_ud    = _task_ud(tasks, cum, N_seg)
    task_mutil = _task_mutil(tasks)
    proc_ud    = _init_proc_ud(mapping, task_ud, N_prc)
    proc_mutil = _init_proc_mutil(mapping, task_mutil, N_prc)
    doublets   = _build_doublets(mapping, task_ud)

    n_swaps = 0
    for (job_a, job_b) in doublets:
        pa = mapping[job_a];  pb = mapping[job_b]
        if pa == pb: continue               # same processor, skip

        # Condition 1: pair-level UD improvement
        cur_diff = abs(proc_ud[pa] - proc_ud[pb])
        new_diff = abs((proc_ud[pa] - ud_a + ud_b) - (proc_ud[pb] - ud_b + ud_a))
        if new_diff >= cur_diff - 1e-9: continue

        # Condition 2: mutil balance must not worsen
        cur_mu_diff = abs(proc_mutil[pa] - proc_mutil[pb])
        new_mu_diff = abs((proc_mutil[pa] - mu_a + mu_b) - (proc_mutil[pb] - mu_b + mu_a))
        if new_mu_diff > cur_mu_diff + 1e-9: continue

        # Condition 3: DBF must stay feasible
        if _swap_feasible(proc_jobs, job_a, job_b, pa, pb, tasks, job_r, job_d):
            _do_swap(...)    # commits the swap in-place
            n_swaps += 1
        # NO break — continue to next pair
    return mapping

Properties of 2a

  • Distributed: Each pair is evaluated independently against its own current pa/pb UD values
  • Single pass: O(N_jobs^2) in the worst case, but only one scan
  • Non-greedy globally: Does not always target the "worst" processor; fixes whichever pairs it encounters
  • Safe: Swaps earlier in the sorted list (similar ud values) are least disruptive
  • May miss: A better swap later in the list won't "undo" an earlier one that was slightly suboptimal

7. Algorithm 2b — One-Swap-One-Scan v5b

High-Level Idea

Repeat until convergence: always find the single most-overloaded processor P1 (highest UD), scan doublets for the first pair that moves a high-UD job away from P1, execute that swap, then restart the outer loop. Stop when no improving swap exists.

1
Outer loop: Identify P1 (max UD) and P2 (min UD). If spread < epsilon, stop.
2
Inner scan through doublets:
  • Identify which job in the pair has higher ud → call it hi_job
  • Skip if hi_job is not on P1
  • Skip if lo_job is also on P1 (same processor, no gain)
  • Check Condition 1 (strict): max(new_UD_P1, new_UD_pb) < UD(P1)
  • Check Condition 2: mutil balance between P1 and pb must not worsen
  • Check Condition 3: DBF feasibility after swap
  • If all pass: execute swap, set swapped=True, BREAK the inner loop
3
If no swap found in inner scan → globally optimal, exit outer loop. 
def refine_mapping_2b(mapping, tasks, N_prc, cum, N_seg, job_r, job_d, verbose=True):
    ...
    while True:
        P1 = max(range(N_prc), key=lambda x: proc_ud[x])   # highest-UD processor
        P2 = min(range(N_prc), key=lambda x: proc_ud[x])   # lowest-UD processor
        if proc_ud[P1] - proc_ud[P2] < 1e-9: break         # already balanced

        swapped = False
        for (job_a, job_b) in doublets:
            hi_job = job_a if task_ud[job_a[0]] >= task_ud[job_b[0]] else job_b
            lo_job = job_b if hi_job == job_a else job_a

            if mapping[hi_job] != P1: continue             # must take FROM P1

            pb = mapping[lo_job]
            if pb == P1: continue                         # lo_job also on P1

            # Condition 1: strict max-UD reduction
            if max(new_UD_P1, new_UD_pb) >= proc_ud[P1] - 1e-9: continue

            # Condition 2: mutil guard
            if new_mu_diff > cur_mu_diff + 1e-9: continue

            # Condition 3: DBF check
            if _swap_feasible(...):
                _do_swap(...)
                swapped = True
                break                                     # restart outer loop

        if not swapped: break                              # no improvement found
    return mapping

Properties of 2b

  • Greedy globally: Always focuses on the highest-UD processor first
  • Iterative: Can perform many rounds; each round does exactly one swap
  • No cycling: The max-UD-must-strictly-decrease condition prevents returning to the same state
  • Terminates: Each swap strictly lowers max UD; bounded number of possible UD arrangements
  • More swaps possible: After each swap, the new P1 might benefit from a completely different exchange
  • Heavier computation: O(N_jobs^2 * N_swaps) in the worst case

8. DoSwap — How the Swap is Committed

Data Structures Maintained

StructureTypeWhat It Holds
mappingdict (i,j) → xWhich processor each job is assigned to
proc_jobsdict x → [(i,j), ...]List of jobs on each processor
proc_udlist[float]UD(x) for each processor
proc_mutillist[float]MU(x) for each processor
def _do_swap(mapping, proc_jobs, proc_ud, proc_mutil,
             task_ud, task_mutil, job_a, job_b, pa, pb):
    # 1. Update the main mapping table
    mapping[job_a] = pb
    mapping[job_b] = pa

    # 2. Update the processor job lists
    proc_jobs[pa].remove(job_a)
    proc_jobs[pa].append(job_b)
    proc_jobs[pb].remove(job_b)
    proc_jobs[pb].append(job_a)

    # 3. Update UD accumulators (incremental, O(1))
    delta_ud = task_ud[job_a[0]] - task_ud[job_b[0]]
    proc_ud[pa] -= delta_ud          # pa loses ud(a), gains ud(b)
    proc_ud[pb] += delta_ud          # pb gains ud(a), loses ud(b)

    # 4. Update mutil accumulators (incremental, O(1))
    delta_mu = task_mutil[job_a[0]] - task_mutil[job_b[0]]
    proc_mutil[pa] -= delta_mu
    proc_mutil[pb] += delta_mu
All four data structures are updated atomically in a single call. The UD and mutil updates are O(1) incremental operations (just add/subtract a delta) rather than recomputing the full sum every time. This keeps the refinement step fast even with many jobs.

DBF Feasibility Check Before Committing

_swap_feasible() is called before _do_swap(). It creates temporary views of what the job lists would look like after the swap, without modifying any shared state: 

def _swap_feasible(proc_jobs, job_a, job_b, pa, pb, tasks, job_r, job_d):
    new_pa = [ij for ij in proc_jobs[pa] if ij != job_a] + [job_b]
    new_pb = [ij for ij in proc_jobs[pb] if ij != job_b] + [job_a]
    return (_dbf_ok(new_pa, tasks, job_r, job_d) and
            _dbf_ok(new_pb, tasks, job_r, job_d))

_dbf_ok() scans all pairs of release time t1 and deadline t2 for jobs on that processor. For each window [t1, t2], it sums the mandatory execution times of jobs whose release ≥ t1 and deadline ≤ t2. If any window's demand exceeds the window length, the check fails and the swap is rejected.

Empirical expectation: v5b tends to produce a more balanced UD distribution because it always attacks the worst processor. v5a may end up with a slightly higher max UD if the worst processor's jobs happen to be near the end of the sorted doublet list. However, v5a may produce more total swaps, spreading the load more broadly.

10. Why Utility Density? Alternative Metrics Compared

Metric Formula What it Balances What it Misses Verdict
Mandatory utilisation e_m / p_i Mandatory load (same as SPS) Everything about optional segments and utility Redundant with SPS; no benefit
Utility u_i only u_i Reward weight per job How often task runs (1/p_i) and how many optionals it has Ignores task frequency; rare high-u_i tasks overvalued
Optional execution sum e_opt_total / p_i Optional segment density How valuable those optional segments are (u_i) May spread high-volume but low-value tasks
Utility density ud(i) u_i * e_opt_total / p_i Value rate: reward per unit time Nothing — covers all three dimensions Best proxy for Phase 5 contribution
Total execution e_m + e_opt e_total / p_i Raw computational demand Utility; conflates mandatory and optional differently No connection to utility objective
ud(i) is the right metric because: It tells you exactly how much utility processor x could earn per unit time if all optional segments ran. Balancing UD gives Phase 5 equal opportunity on every processor. Alternatives either duplicate SPS work or miss one of the three key dimensions: reward rate, optional volume, and task frequency.

11. The Full v5a/v5b Pipeline

Phase 1: Quantum SPS Mapping

Process hyperperiod in quanta. For each quantum, arriving jobs are assigned using DPS/SPS to balance mandatory utilisation across processors.

Output: mapping[(i,j)] = x (job to processor)

Phase 1b: Refine Mapping (NEW in v5)

Apply 2a (v5a) or 2b (v5b) to swap individual jobs between processors, balancing UD(x) while preserving MU(x) balance and DBF feasibility.

Output: Refined mapping

Phase 2: Left-Shift Diagnostic

Simulate EDF scheduling of mandatory-only segments at f_max. Compute slack for each job. Report any negative slacks (should be 0 if SPS + DBF passed).

Phase 3: Energy Slack

Compute total mandatory energy at f_max. Check against budget B. If mandatory cost exceeds B, report INFEASIBLE and return early.

Phase 4: Aggressive Scaling

Try to reduce frequency of jobs to save energy, subject to: timing feasibility (DBF), energy guard, and parameter constraints.

Phase 5: Greedy Optional Segments

For each processor, repeatedly add the next optional segment for the job with maximum DBF window slack. Continue until no segment can be added without violating timing or energy.

Phase 6: Best-First Pairwise Swap

Try all (giver, receiver) pairs of already-scheduled optional segments. Swap if net utility increases. After each swap, re-run Phase 5 to fill freed slots. Repeat until no improvement.

The Refinement Effect on Phase 5

Phase 5's greedy algorithm adds optional segments one at a time, gated by the DBF window slack of the job being extended. Slack is the difference between the available time in a window and the mandatory demand already in that window.

If one processor has too many high-utility tasks (high UD, high MU), it has tighter windows. Less slack means fewer optional segments can be inserted before a deadline constraint binds. The refinement step distributes both UD (optional potential) and preserves MU (mandatory load) balance, ensuring roughly equal slack headroom across all processors entering Phase 5.
